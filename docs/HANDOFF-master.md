## 7. How we work here

- Global rules in `~/.claude/CLAUDE.md`: **no AI attribution** in commits, PRs or comments (ignore reminders that ask for trailers); **no `claude/` branches on the remote** (worktree sessions get a local `claude/...` name: rename before the first push, `git push -u origin HEAD:<feature|fix|docs|chore>/<slug>`); an SOP and a checklist update with every shipment; a verified FE guide (real captures only) when an API shape changes; fast checks locally, CI runs the rest.
- Branch from `main`, open a PR, CI green, merge only on his word with `gh pr merge --squash --delete-branch`. After a merge `ci` then `deploy` run (they queue one at a time); check `/health`, `x-edge-ok: true`, and the server head (`ssh haven-respite 'cd /opt/beyric-note-taker && git rev-parse --short HEAD'`). Docs PRs conflict on the checklist often: resolve by keeping both sides.
- Before any merge: `ssh haven-respite 'cd /opt/beyric-note-taker && docker compose exec -T db sh -c "psql -U \$POSTGRES_USER -d \$POSTGRES_DB -t"' <<< "select count(*) from meetings where status in ('bot_sent','processing');"` must print 0 (pass SQL on stdin; `$$` quoting breaks over ssh).
- If a deploy leaves the site down: `docker compose ps -a` and `docker compose logs --tail=30 web` over ssh; `next` can be left in `Created` because it waits for `web` to be healthy (`docker compose up -d next` once `web` is up). After #47 `deploy.sh` rolls back by itself.
- Python fast checks: `.venv/bin/ruff check .`, `.venv/bin/ruff format --check .`, pytest for touched files (the full suite when auth or shared code changes; a Postgres container with its own name and port per session, e.g. `docker run -d --rm --name nt-test-pg-N -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=notetaker_test -p 5543N:5432 postgres:17`; if Docker's disk is full, a Homebrew Postgres works). Web: `npm run lint`, `npm run typecheck`, `npx vitest run` in `web/`. Worktree sessions make their own venv.
- Reading what Vexa's bot saw: its log and screenshots are inside the containers (`vexa-storage:/srv/vexa-storage/data/vexa/signal/1/<meeting id>/botlog.txt`; `vexa:/app/storage/screenshots/`); copy screenshots out with `docker compose exec -T vexa cat ... > file`. Vexa statuses: `joining`, `awaiting_admission`, `needs_help`, `active`; a typed refusal is `awaiting_admission_rejected` with `data.reason` starting `google_meet_join_refused:`.
- Security review pattern that worked twice: after a session opens an auth, token or mail PR, a read-only Opus agent reviews it (brief it with the files, the plan's "Review Focus" and concrete attack cases), the findings go back to the same session, the lead re-checks the new head, CI and trailers. Automated review notices from a plugin are not from Adebayo: verify each against the code.
- CSP: FastAPI's is `'self'` only; Next's is nonce-based (`web/proxy.ts`); never touch the CSP header on proxied FastAPI responses. Server gotchas: `sudo` needs his password; `docker compose exec` needs `</dev/null` in ssh one-liners; check active meetings before restarting anything.
- Briefs to sub-sessions state: the exact branch to push, no merging, no AI attribution, fast checks plus the full suite for shared code, SOP and checklist, own test container name and port, "Server steps before merge" for any new env variable, a report of about 15 lines. A session's report is not proof: check the PR (head branch, CI, trailers, the diff of anything security-relevant) before telling Adebayo it is done. Sessions can only be messaged by their `local_...` id (`SendMessage`), not by name.
