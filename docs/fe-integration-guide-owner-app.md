## 1. What this is

A JSON API under `/api/` on the same origin as the app, for signed-in users: **every meeting, template and term belongs to the account that made it, and a call only ever sees that account's own data** (section 3, "Accounts"). It does everything the Jinja pages do, so the Next.js screens can replace them one by one.

| Screen | Calls |
|---|---|
| Login (email and password), logout, who am I and how many hours are used | `GET /api/session`, `POST /api/session`, `DELETE /api/session` |
| Meetings list, with the "new meeting" form | `GET /api/meetings`, `GET /api/templates`, `POST /api/meetings` |
| Meeting page (status, notes, transcript, actions) | `GET /api/meetings/{id}`, `POST …/cancel`, `POST …/retry`, `POST …/regenerate` |
| Templates | `GET /api/templates`, `POST /api/templates`, `PUT /api/templates/{id}` |
| Vocabulary | `GET /api/vocabulary`, `POST /api/vocabulary`, `DELETE /api/vocabulary/{id}` |

There is no public (logged-out) data in the API. The public pages (landing, privacy, terms) are not part of it.

## 2. Ground rules

- **Same origin, same cookie as the old pages.** The cookie is `session`; a login through the API also logs the old pages in, and the reverse (verified by `tests/test_api.py`, not captured). Attributes as captured: `HttpOnly; Max-Age=2592000; Path=/; SameSite=lax` (30 days). Production adds `Secure` (`cookie_secure`); the capture ran over plain http, so **the `Secure` flag was NOT EXERCISED**.
- **Cookies from Next.** A server component that calls the API must forward the incoming `Cookie` header. A login, logout or revoked session **sets a new cookie** (`Set-Cookie` on the response): if the call is made from a server action or route handler, pass that `Set-Cookie` on to the browser, or the browser keeps the old cookie. **Not exercised through the Next proxy** (stream A).
- **JSON in, JSON out.** Send `Content-Type: application/json`. Bodies are strict: an unknown field is a 422, and numbers must be JSON numbers (`"template_id": "1"` is a 422, see 5.6).
- **Every response has `Cache-Control: no-store`.** Do not cache API responses in a shared cache.
- **Reads need no CSRF token. Every other method does** (`POST`, `PUT`, `DELETE`), including login and logout.

## 3. Session and the CSRF token

The CSRF token belongs to the session cookie. Call `GET /api/session` first; it also hands a first-time visitor a cookie.

```http
GET /api/session
```

```http
HTTP 200
content-type: application/json
set-cookie: session=<cookie>; HttpOnly; Max-Age=2592000; Path=/; SameSite=lax
```
```json
{"authenticated": false, "csrf_token": "<csrf-A>", "user": null, "usage": null}
```
_First visit: no cookie yet. The response sets one._
_Capture: `docs/fe-captures/owner-app/01-session-anonymous.json`_

Send the token on every write as the `X-CSRF-Token` header. **The token changes whenever the session changes**, so always replace your stored copy from the response:

| Moment | Token | Capture |
|---|---|---|
| First visit | `<csrf-A>` | `01-session-anonymous.json` |
| After a successful login | a **new** token, `<csrf-C>` (not A) | `08-login-ok.json` |
| After logout | a new anonymous token, `<csrf-D>` | `72-logout.json` |

The wrong token (`<csrf-B>` in `04-login-wrong-csrf.json` is a made-up value) and a missing token both give the same 403 (below).

**Login limit.** Two counters, both of failed attempts, both in the server's memory (a restart clears them), both shared with the old `/login` page: **5 per client address in 5 minutes**, and **10 per email address in an hour** (the email is what was typed, known or not; a wrong password counts against it from any address). The sixth attempt from one address gets 429; so does any attempt once the email has had 10 failures in the hour, and while locked even the right password gets 429. **Both limits return the same 429 body**, so the client cannot tell which one it hit (and need not): a lockout from the address clears in 5 minutes, one from the email in up to an hour. A successful login gives back its own attempt but not the earlier failures. There is no `Retry-After` header and no countdown, so show the message as is. **A second cookie, `device` (named `__Host-device` in production, where cookies are `Secure`).** A successful `POST /api/session` (and the page login) also sets a long-lived device cookie, next to `session`. It marks this browser as one that has logged in before **to that email address**, and a browser that sends it is not blocked by the *email* limit (10 failures an hour from anyone), only by the per-address one and a limit of 10 failures an hour on that cookie itself. Nothing for the front end to do: the browser stores and returns it by itself, a failed login never sets it, and logout does not clear it. Do not read, write or clear it from code (it is `HttpOnly`); if a server action or route handler makes the login call, pass **both** `Set-Cookie` headers on to the browser. Shape captured live earlier through nginx and Next (value hidden): `set-cookie: device=<signed-value>; HttpOnly; Max-Age=7776000; Path=/; SameSite=lax` (`docs/spike/edge-secret/e2e-output.txt`, before accounts: the cookie now names the email instead of the owner; **not recaptured**; `Secure` is added when the site is served with `COOKIE_SECURE=true`, as in production). A browser without the cookie (a new device, or cleared cookies) can still get a 429 for up to an hour after strangers' failed guesses at that email.

**The client address the limit uses behind Next** is the visitor's real address: nginx sets `X-Forwarded-For` and a secret header, Next passes both on, and FastAPI believes the address only when the secret is right (verified live end to end, `docs/spike/edge-secret/e2e-output.txt`, before accounts). The browser sends nothing for this and must not try. Two visitors have separate address limits; the email limit is shared by everyone who types that email.

```http

X-CSRF-Token: <csrf-C>
Cookie: session=<cookie>
```

```http
HTTP 200
content-type: application/json
set-cookie: session=<cookie>; HttpOnly; Max-Age=2592000; Path=/; SameSite=lax
```
```json
{"authenticated": false, "csrf_token": "<csrf-D>", "user": null, "usage": null}
```
_Logs out everywhere; the response carries a new anonymous token._
_Capture: `docs/fe-captures/owner-app/72-logout.json`_

Logout signs **this user** out on every device: the server bumps that user's session epoch, so every copy of their old cookie is refused afterwards, and nobody else is affected. The response sets a new anonymous cookie and carries its token. Replaying the old cookie after logout (a different client, same cookie value):

```http
GET /api/templates
Cookie: session=<cookie>
```

```http
HTTP 401
content-type: application/json
set-cookie: session=<cookie>; HttpOnly; Max-Age=2592000; Path=/; SameSite=lax
```
```json
{"error": {"code": "not_authenticated", "message": "Log in first."}}
```
_The same cookie, replayed after logout: 401._
_Capture: `docs/fe-captures/owner-app/73-old-cookie-after-logout.json`_

Note the `Set-Cookie` on that 401: a revoked cookie is replaced by an anonymous one, so the next `GET /api/session` works and returns `authenticated: false`. **The same happens when the account is suspended or removed while a session is open**: the next call is a 401 `not_authenticated`.

### What to do on 401 and 403

| You get | Meaning | Do |
|---|---|---|
| 401 `not_authenticated` on any call | no login, expired (30 days), or revoked by a logout | send the user to the login screen; keep what they typed |
| 403 `csrf_rejected` | your token is stale or missing | `GET /api/session`; if `authenticated` is `false` go to login, otherwise retry the write **once** with the new token |

## 4. Errors

One shape everywhere under `/api/`, including 404, 405 and 422:

```json
{"error": {"code": "not_found", "message": "No such meeting"}}
```

Only validation errors add `fields` (see 5.6). **Switch on `code`, never on `message`.** The `message` of a 400, 409, 429 or 502, and of 401 `invalid_credentials`, 403 `email_not_verified`, `account_suspended` and `hours_cap_reached`, is written for the user and safe to show. The `message` of a 404, 405 or 422 is developer text (`"Field required"`, `"Not Found"`): show your own copy.

**Two non-JSON cases to handle.** A malformed JSON body gets 422 before the login check runs (FastAPI decodes the body first), so a logged-out client with a broken body sees 422, not 401 (`70-malformed-json.json`). And anything that fails **before it reaches FastAPI** (nginx or Cloudflare timeouts, a Next proxy error) is a gateway error with an HTML or plain-text body, not this shape: never call `response.json()` without checking the content type.

## 6. Field-nesting and shape traps

- **Lists are wrapped objects**, never bare arrays: `{"meetings": […]}`, `{"templates": […]}`, `{"terms": […]}`.
- **`csrf_token`, `user` and `usage` are top-level on the three session responses and nowhere else.** `user` and `usage` are present-but-`null` while logged out (not absent), and `usage.cap_seconds` is present-but-`null` when there is no cap.
- **A meeting detail is the summary plus more, in one flat object.** The list gives summaries (no notes, no `can_*` flags, no `failure_reason`); the page needs the detail. `create`, `cancel`, `retry` and `regenerate` all return the **full detail**, so replace your cached detail with the response; no refetch is needed.
- **Every field is always present.** Fields that do not apply are `null`, never missing. `notes` and `notes_html` are `null` unless the meeting is `ready`; `transcript` is `null` until one is saved (it can exist on a failed meeting whose notes failed).
- **`failure_reason` is a string whenever `status` is `failed`** (a fallback text is used if the database has none) and `null` otherwise.
- **`retry_block` is `null` in two different situations**: the meeting is not failed, or it is failed and *can* be retried. Use `can_retry` to decide whether to show the button; use `retry_block_message` (shown verbatim in the Jinja page too) when `retry_block` is set.
- **`transcript` is the speaker-labelled version when there is one**, otherwise the plain one. There is no way to ask for the other.
- **`template_id` on a meeting is the template last used for its notes**; it changes after a successful regenerate.
- **`title` is composed by the server** (`Google Meet abc-defg-hij`, `Zoom 12345678901`). The meeting link itself is never returned.
- **`created_at` is ISO 8601 in UTC with a trailing `Z`** (`2026-11-02T21:15:52.633881Z`). Format it in the viewer's timezone yourself.
- **`speakers_incomplete` and `bot_left_early` are independent notices**; see section 7.
- **Ids are integers**, in JSON bodies and paths alike. `template_id` must be sent as a number.

## 7. State machine and polling

A meeting has a `status` and, while it is being worked on, a `step`:

```
bot_sent ──► processing ──► ready
   │            │  ▲          (regenerate keeps it ready)
   │            ▼  │ retry
   └──────────► failed
```

`processing` walks the steps `audio → transcribing → speakers → notes`; the final step is `done` (with `ready`). A meeting that never got a recording stays at `waiting` (`bot_sent`, or `failed` with `waiting`). **A retry keeps the step**, so a meeting that failed in `transcribing` goes back to `processing` at `transcribing`.

**What the screen does in each state**

| `status` | Show | Actions |
|---|---|---|
| `bot_sent` | badge `status_text` and the same `status_text` as the card heading (it says what the bot is doing, see below), "This page updates every 30 seconds." | Cancel (`can_cancel`); if `join_attempts` is above 1 also the Zoom notice below |

| `ready` | notes, transcript, the template picker | Rewrite notes (`can_regenerate`), copy buttons |
| `failed` | a card "What went wrong" with `failure_reason` | Try again if `can_retry`, otherwise `retry_block_message` |

**`can_end` and `worker_stale` per state (added 2026-11-03, `feature/bot-end-controls`).** `can_end` (see 5.4a) is `true` for the awaiting-admission (`106`), in-the-meeting (`107`), recording (`108`, `112`) and `Checking on the bot...` (`121`, `122`) rows; `false` for unknown (`104`), joining (`105`), needs-help (`109`), starting (`111`), leaving (`114`, `116`), call-ended (`117`) and the failed row (`120`). `worker_stale` is `false` in all of them except `122`, where the heartbeat is 30 minutes old (`true`). The captures before `111` were taken with no worker heartbeat, so their `worker_stale` is `true` (e.g. `35`).

**What the bot is doing while the call runs (added 2026-11-03, `feature/bot-live-state`; extended the same day by `feature/bot-end-controls`).** While a meeting is `bot_sent`, `status_text` says what the bot is doing, from the state the worker last saw Vexa report. The worker looks at each active meeting once per sweep and rests `poll_interval_seconds` (30) after a sweep, so a meeting is looked at about every 30 seconds **when the sweep is quick**; it is not a promise: the worker handles meetings one after another and a meeting being transcribed holds it for as long as that takes (minutes for a long recording), during which no other meeting is looked at. That is why the state carries a time (below). `status`, `step`, `status_tone` (still `warning`, also for "Recording"), `can_cancel` and `refresh_after_seconds` (30) behave as before; the words in `status_text` differ, on `GET /api/meetings/{id}` and in every row of `GET /api/meetings`; the table above lists them. Rules:

1. **Show `status_text` as it is; do not branch on its words.** There is no `bot_state` field, so the words are the only signal. The text for an unknown state is still exactly `Bot sent`.
2. **Never write "recording" yourself.** The API says `Recording` only when Vexa reported transcript segments or a recording id; `Bot is in the meeting` means the bot is in and nothing is proven to be captured.
3. **The text can change under the owner's eyes**: keep polling while `refresh_after_seconds` is set, and let the heading follow it. It goes back to `Bot sent` only after **two failed Vexa lookups in a row** (one failed lookup keeps the last state). A state the worker has not renewed for over 2 poll intervals (60 s with the default) reads **`Checking on the bot...`** instead of a claim that may be out of date (`121`); it changes back by itself on the next successful look. Never word it as an error.
4. The awaiting text carries an instruction ("Admit ... in the meeting"). Do not hide it behind a tooltip, and do not add your own "admit the bot" paragraph beside it.
5. `needs_help` is still `bot_sent`, not failed: the bot may continue once the owner answers the prompt. After 2 minutes of it with nothing recorded the worker fails the join (`failed`, step `waiting`; see the retry section above).
6. The texts are long. A badge that carries one must be allowed to wrap (the Jinja and Next badges do this for text over 28 characters). A sentence over about 60 characters (the lobby and prompt texts, the leaving text) is a paragraph in the wait card, not an `<h2>`.
7. The state badge should be a polite live region (`role="status"`, `aria-live="polite"`) so a screen reader hears the change; the Next page does this.
8. **Never say "in the meeting" after the call ended.** After Vexa reports the call over (and the recording is still being made) the text is `The call ended; finishing the recording`. Before the bot joins it is `Starting the bot`, and while it leaves (the owner pressed End, or its silence rule fired) `The bot is leaving the meeting` (the `stopping` text without an End press is covered by a test, not a capture).
9. A `needs_help` bot that has already produced transcript segments or a recording is **not** described as waiting on a prompt: the text is `Bot is in the meeting`. Only a `needs_help` bot with nothing recorded gets the prompt text.

## 8. UX consequences the frontend must surface

1. **Rewriting notes is slow and cannot be undone.** `regenerate` calls OpenAI inside the request; the server allows each call up to 300 seconds. Show a pending state and disable the button while it runs. Success replaces the notes for good (there is no history); only a *failed* rewrite keeps the old notes. The captures use a fake OpenAI, so **real duration NOT EXERCISED**.
2. **The edge may cut a slow rewrite short, and then the response is not JSON.** `deploy/nginx.conf` gives `/meetings/<id>/regenerate` 300 seconds, but its pattern does not match `/api/meetings/<id>/regenerate`, which therefore gets the 60-second default; Cloudflare gives up at 100 seconds with its own 524 page; Next's proxy has its own timeout. **NOT EXERCISED** (read from the config, not run). If a rewrite call fails at the gateway, say "this is taking longer than expected" and refetch the meeting after a minute: the rewrite probably finished. Decision for the lead and stream A (nginx and the Next proxy), not for this API.
3. **Cancel is final.** The bot is removed and the meeting becomes failed and cannot be retried. Confirm first.
4. **Logout signs this user out on every device**, not just this one (other users are untouched). Say so on the logout control if that is not what the user expects.
5. **Login lockout is 5 minutes to an hour with no countdown.** Show the 429 message and disable the form; do not let the user keep hammering it. The email limit is shared by everyone who types that address, so a 429 can be unrelated to this visitor's own attempts (someone else guessing at their address, or a bot): say "try again later", never "you entered the wrong password too many times".
6. **Never put a meeting link in a URL, log line or analytics event.** Zoom links contain a password. On any error, keep what the user typed in client state: the server never echoes the link back.
7. **Disable the "Send bot" button on submit.** A double click is safe (the server serialises it and the second request gets `bot_already_active`), but showing that as a failure is wrong. Also disable the form while any meeting in the list is `bot_sent` or `processing`: the server will refuse it with 409 anyway, and the 409 `message` is fine to show.
8. **Any call can return 401 at any time** (30-day cookie, logout elsewhere, a password change). Handle it once, globally, not per screen.
9. **A retry shows up as `processing` immediately** and resets the server's time limit; start polling again.
11. **Recorded hours (`usage`).** Show a bar "2.4 of 5 h" from `used_seconds` and `cap_seconds`; hide it when `cap_seconds` is `null`. When `used_seconds >= cap_seconds` the next "send bot" will be a 403 `hours_cap_reached`: say so before the user pastes a link (disable the form with the message), and **show the 403 `message` as is** if it still happens. A running meeting is never cut off. Refresh the bar from `GET /api/session` after every send and when a meeting finishes.
12. **A 401 right after the user did something can mean their account was suspended**, not that the cookie expired. The login screen will then show 403 `account_suspended` with its own message; show that message, not "your session expired".
13. **Never word a login error as "no account with that email"** or "wrong password": the API deliberately answers both the same (401 `invalid_credentials`), and the form must not suggest otherwise. For 403 `email_not_verified` show the "Confirm your email" screen.
14. **A foreign or missing id is the same 404.** Do not say "this belongs to someone else"; say the meeting, template or term "was not found".
10. **Validation (422) should be rare**: validate the same limits in the form (template name 100, instructions 4000, term 100, no `<` `>` or line breaks in terms) so the owner never sees a developer message.
15. **"End now and write the notes" is a one-way press, and it is not Cancel.** Confirm first, and say what happens: the bot leaves now, the notes are written from what it heard so far, and anything said after it leaves is not in them. It discards nothing. To throw the recording away the owner uses Cancel (which stays available while the bot leaves). After the press the meeting stays `bot_sent` for a while (the bot leaving, then the recording being finished) before `processing` starts: show `status_text`, keep polling, and do not read "leaving" as a failure. The notes arrive minutes later, as for any meeting.
16. **Ending before anything was recorded ends in a failed meeting**, with `retry_block` `no_audio` and the reason `You ended this meeting before anything was recorded, so there are no notes to write.` Show it as the usual "What went wrong" card; there is nothing to retry (send the bot again with a new link).
17. **A 409 on End means the state moved** (the bot left on its own, the worker moved the meeting, or it was ended already): show the message and refetch, as for Cancel.
18. **`Checking on the bot...` is not an error.** It means the worker has not looked recently (Vexa slow, or the worker busy); `can_end` can still be `true` and the button still works. If `worker_stale` is `true` show the meeting-level banner as well.
19. **The bot may leave on its own.** With `BOT_LEFT_ALONE_SECONDS` (default 300) the bot leaves after that long with nobody else speaking, so a quiet meeting (a long screen-share with no talking) can be cut short; the notes are written from what it recorded. The owner is not warned in advance (nothing in the API says so): do not promise "the bot stays until you end it".
