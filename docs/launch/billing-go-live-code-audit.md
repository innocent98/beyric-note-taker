# Billing go-live code audit: everything that depends on `BILLING_LIVE` or on test data

Audited 2026-11-21 on `main` at `f1509bc6` (Alembic head 0054). Read-only: nothing in this PR changes code. The runbook that uses this audit is `docs/launch/billing-go-live-runbook.md`; the questions for Adebayo are in `docs/launch/billing-go-live-questions.md`.

Everything below was read in the code. **Nothing was run against a live provider**, so each "what the provider answers" is marked NOT VERIFIED where the code only handles it.

## The finding that matters most: what the flip does to rows made with test keys

The database does not know which mode a row was made in. `BILLING_LIVE` is a process setting, and no table has a test marker except `invoices.test_mode` (`app/models.py:1061`, `app/billing/invoices.py:199`). `payments`, `subscriptions`, `payment_methods`, `hour_grants` and `refunds` carry nothing. So on the day the keys flip, every test row is read as live, and the live provider is asked about test references and test card tokens.

What each kind of row does after the flip (read from `app/billing/renewals.py`, `subscriptions.py`, `settle.py`, the two adapters):

| Test-mode row | What happens after the keys flip | Verdict |
|---|---|---|
| **Active subscription, period not over yet** (most of them: a test plan bought on or after 2026-11-17 runs a month) | Nothing at once. The person keeps the plan and its hours, **for free**, until `current_period_end`. Then the renewal runs (next two rows). A person with a live row also cannot buy: `start_plan_checkout` answers 409 `already_subscribed` (`app/billing/subscriptions.py:215`) | NEEDS A CHANGE |
| **Renewal of a Paystack test subscription** | `renewals._attempt` reads the saved TEST authorization code (`subscriptions.saved_card`, `subscriptions.py:328`) and sends it to `POST /transaction/charge_authorization` with the LIVE key (`paystack.py:390`). Paystack's live side does not know a test code, so the answer cannot be a paid charge. What it answers is NOT VERIFIED. **Every answer except "HTTP 200 with a clean `failed` transaction" ends in `ProviderError`** (`paystack.py:495-522`: 4xx, 5xx, a timeout, an unexpected shape). Then `renewals.py:292-303` asks `verify_reference` for our new reference, gets `ProviderError` again (404, no such payment) and **returns with the payment left `pending` and the subscription still `active`**. No failure is counted, no grace opens, no mail goes out. Every 60 seconds the clock picks the subscription again (`run_due`, `renewals.py:105`), finds the pending payment (`_settle_open_payments`, `renewals.py:364-441`), asks the live API once more, and waits. After six hours it tells the admins once (`renewals.py:392-400`). **It never ends.** Meanwhile the person is read as past due and then lapsed by the clock (`states.effective_status`, `states.py:177-192`), so hours and gates close, but the row stays `active`: checkout says `already_subscribed` and the pay link says `provider_error` 502 (`renewals.py:798-807`). **The person cannot pay at all** until someone closes the row by hand | **NEEDS A CHANGE (blocks go-live)** |
| **Renewal of a Flutterwave test subscription** | `charge_saved_method` posts the test token to `POST /v3/tokenized-charges` with the live key (`flutterwave.py:485-487`). The adapter's own note says Flutterwave answers HTTP 400 for a bad token (`Wrong token or email passed`, `flutterwave.py:459-461`, from the vendor page, NOT VERIFIED live). A 400 becomes a `failed` transaction (`flutterwave.py:489-498`), so the normal path runs: attempt 0 fails, `past_due`, grace 72 hours, three mails to a person who never paid ("We could not renew your plan", "Last day to pay", "Your plan has ended", `renewals.py:182-198`), then `lapsed`. Clean, but the mails are false to the person and the lapse removes hours they had | NEEDS A CHANGE |
| **Double charge risk** | None found. A live provider cannot charge a card from a test token: the adapters refuse a call without a token and the live side has no record of a test code. NOT VERIFIED on a Paystack page (its pages say test and live data are separate, not that tokens are separate). The settlement rules (`settle.py`) still require our reference, our currency and at least our amount before any hours | OK |
| **Pending test payments** (an abandoned test checkout) | The sweeper asks the live provider by reference for payments up to 3 days old, and for failed plan, pack or upgrade checkouts up to 7 days old (`renewals.py:73-80`, `628-716`). Paystack answers 404 (`ProviderError`, ignored), Flutterwave `NoRecord` (a `ProviderError`, ignored). Harmless, but it adds live API calls and puts "Payments have waited more than a day" in the admin alerts (`renewals.py:569-596`) | OK (noise) |
| **Unprocessed test webhook events** in `billing_events` | `_sweep_events` retries events of the last 3 days with the live adapter (`renewals.py:599-625`); the re-read fails and the event stays parked | OK (noise) |
| **Hour grants made by test payments** (`plan_period` grants with a `subscription_id`, `pack` grants with a payment id and a 12-month expiry) | They stay in force. A test pack is **10 free hours valid 12 months**. Nothing marks them as test | NEEDS A CHANGE |
| **Saved test cards** (`payment_methods`) | Kept, encrypted. `saved_card` takes the newest card of that provider (`subscriptions.py:331-335`), so a person's later live card wins; a person whose live payment left no reusable token would be renewed with the old test token | NEEDS A CHANGE (deleted by the closeout) |
| **Test invoices and payments in the person's lists** | Listed and downloadable with numbers `BN-2026-9000NN` (`invoices_api.py:98-109`, `130-134`; `subscriptions_api.py:384-398`) for payments where no money moved. See "Test-era invoices" below | NEEDS A CHANGE |
| **First-payment refund rule** | `refunds._is_first_plan_payment` (`refunds.py:120-136`) takes the earliest plan payment the person ever made, test or live. **A person who bought a test plan before go-live cannot have their first live payment refunded from the admin screen** (409 `not_first_payment`). This hits Adebayo's own accounts if he reuses one | NEEDS A CHANGE (and a runbook rule: pay with fresh accounts) |

### Recommended safe handling: a one-time closeout, run just before the flip

Not written in this PR. Design below; estimate at the end.

`scripts/billing_close_test_data.py`, default a dry run that prints counts only (no names, no emails, no tokens), `--apply` to change data, one transaction per person, refusing to run unless a cutover time is given.

1. **Cutover time `T`** (UTC, passed as `--before`): every row created before `T` is test-era. `T` is the time the closeout is run, and the same value is put in `BILLING_LIVE_SINCE` in the `.env` edit that follows within minutes. Nothing made after `T` is touched. (A test purchase made in the few minutes between the closeout and the restart would be missed: nobody should buy anything in that window, and the dry run's counts are read again after the restart.)
2. Subscriptions with `created_at < T` and status `active` or `past_due`: set `status = 'ended'`, `next_charge_at = null`, `canceled_at = now` (the `ended` status exists, `states.py:38-41`, and is a history status that never charges, never renews and no longer blocks checkout, because `live_row` reads only `active` and `past_due`, `subscriptions.py:132-139`). No mail (the script does not go through `renewals._close`).
3. Hour grants of kind `plan_period` or `pack` whose `source_payment_id` points at a payment created before `T`: set `expires_at = now` (the same move `subscriptions.end_leftover` makes, `subscriptions.py:547-559`). Trial, pilot and admin-gift grants are never touched.
4. Saved cards (`payment_methods`) created before `T`: delete.
5. Payments `pending` and created before `T`: set `failed` (no `pay_url` call, no provider call).
6. Never delete payments, invoices or refunds (money records). They stay as history.
7. Print a before and after count table and a one-line "PROOF: OK" only when the after counts are zero for live test-era subscriptions and test cards.
8. Take a database backup first (`deploy/backup.sh`), and keep it.

A second, small change goes in the same PR: **`BILLING_LIVE_SINCE`** (an ISO timestamp setting, default empty). When set, the person's invoice list and PDF route, the payments list, `subscriptions_api._invoice_numbers` and `refunds._is_first_plan_payment` ignore rows created before it. It is the same `T` the script uses, so there is one rule: "before `T` is test-era and is not shown, not counted". It also covers the test payments that have no invoice, which `invoices.test_mode` cannot (a failed or pending payment never gets an invoice).

**Rejected alternatives.** (a) Do nothing and accept the stuck Paystack rows: people cannot pay and the clock calls the live API forever. (b) Wait until every test subscription has renewed or lapsed under test keys: they renew successfully in test mode, so they never end. (c) Run raw SQL by hand on the server: money rows, no review, no dry run. (d) Add a `test_mode` column to payments and subscriptions: a migration on money tables for a one-time event, when a cutover time does the same job.

**Estimate:** about one day of one Sonnet session (script, `BILLING_LIVE_SINCE` filter in five places, tests on a scratch database) plus an Opus review, because it edits subscriptions, hours and cards. **Go-live waits for it.**
