# SOP: Send now, Not recorded, and the mail's "Send it again" button (C15b)

## What shipped
When the note taker did not get into a calendar meeting the person can now see it and ask again:
`GET /api/not-recorded`, `POST /api/scheduled-joins/{id}/send-now`, three new fields on the
Upcoming rows, and the "Could not join" mail's **Send it again** button (a link to the Meetings page, `/`).
Backend PR `feature/c15b-send-now` (number on the PR page; not merged by the author). The screens
are a second PR (`feature/c15b-send-now-screens`); their section is at the end of this file.

## Why
Calendar auto-join is live, but a join that failed, found no capacity or was skipped had no way
back: the "Could not join" mail said "you can send it again" with no button behind it, and the
Meetings page did not list meetings the note taker never got into. Spec 7.7 and plan task C15b.

## How
- **One placement path.** Send now does not send a bot itself. `app/send_now.py` takes the join row
  under the same two locks the runner uses (event row first, then the join, both `FOR UPDATE`) and
  calls `placement.place_bot(wait_seconds=0, on_placed=...)`, the one function that runs the
  pre-flight (hours cap, per-user limit, one bot per code, capacity) under the placement lock. The
  `on_placed` hook marks the join `joined` in the same transaction as the meeting row, exactly as
  the runner does. Nothing is bypassed, and two placements cannot happen.
- **Idempotent.** A second press waits on the row lock, finds the join `joined`, answers 200 with
  the same meeting and sends nothing. A runner tick after a click finds the row `joined` and skips
  it; a click after a runner tick finds it `joined` too.
- **A refusal changes nothing.** The pre-flight's refusals come back with the pasted link's codes
  and words (`services.placement_refusal`) and the row is left as it was. Decision: no hidden retry
  after a refusal (the alternative, putting a refused row back into the runner's 15-second retry for
  15 minutes, was rejected: the person would be told "busy" and a bot could arrive later without
  being asked). The `deadline_at = now + 15 min` of spec 7.7 is written when the send succeeds.
  If the placement lock is held by another send (`bot_busy` with `slot_locked`) the call waits up
  to 3 seconds, letting go of the row lock between looks and re-checking everything each time.
- **One rule.** `calendar_text.send_now_block(join, now)` decides, for the route and for the lists
  (`can_send_now` is `send_now_block(...) is None`), so the button and the server cannot disagree.
  Allowed: `failed`, `no_capacity`, or `skipped` for a Not recorded reason, once the meeting's moment
  has come (`run_at <= now`) and while `now <= ends_at`; never for `account_suspended` (403). Not on
  the list: 409 `cannot_send_now` (still scheduled, switched off, done). Not started yet: 409
  `not_started` ("This meeting has not started yet."): a lapsed calendar marks future joins
  `skipped / needs_reconnect` and Upcoming exposes their ids, and a send into an empty room days early
  would take a slot, fail, and leave the real meeting unrecorded (found in the Opus review of #145).
  After the meeting ended: 409 `meeting_ended`. Another person's join: 404 `not_found`.
- **Orphans and templates.** The request sets `adopt_orphan` as the runner does, so a bot of the
  person's own that a killed earlier send left on the code is adopted instead of answering "a note
  taker is already there". The calendar template is checked before the send (409 `template_required`);
  any other `ValueError` from placement is a caller bug: the locks are let go and it is a 500.
- **Not checked, on purpose.** The calendar connection's state (the link is stored; a lapsed
  calendar does not stop a bot being sent to a meeting that is on) and the join rule (the person
  is overriding it by asking). Spec 7.7 names hours, concurrency, dedupe and capacity as the
  pre-flight, which is what `place_bot` runs.
- **The list.** `GET /api/not-recorded`: the caller's joins from the last seven days whose
  `run_at` has come and that never produced a meeting (`meeting_id` null): `failed`, `no_capacity`,
  and `skipped` with reason `hours_cap`, `user_limit`, `code_in_use`, `meeting_has_note_taker`,
  `needs_reconnect` (the spec calls it `calendar_disconnected`; the code stores `needs_reconnect`,
  both are accepted) or `account_suspended`. A join that dispatched and failed is a meeting row.
  `duplicate_meeting` IS in the list, as spec 7.7 has it (the runner also gives it when the person's
  own bot is or was in that room because they pasted the link: the text says so, and Send now is
  still allowed, because placement refuses with its own words while that bot is there). One
  constant: `calendar_text.NOT_RECORDED_SKIP_REASONS` (which also has `refused`, the runner's
  catch-all). A join that dispatched is `joined` or `completed`, never listed.
- **Upcoming rows** carry `join_id`, `can_send_now` and `not_recorded_text` (same words as the list)
  so the Upcoming list can draw the button without a second call.
- **The mail.** `mail_templates.SEND_AGAIN_PATH = "/"`: the designer's own sentence is
  "Send it again from the Meetings page", and the Meetings page is the app's home (`/`; there is no
  `/meetings` page, a GET there is not a Next page). A visitor who is not signed in sees the landing
  page with its Log in link. A plain link into the signed-in app: no token, no query,
  nothing happens by opening it (a mail scanner or a forwarded copy cannot send a bot). Rejected:
  a link that sends in one click (an email link must never act), and a token in the URL.

## Verification
`tests/test_send_now.py` (42 tests): success marks the join `joined`, creates the meeting with the
event's title and `calendar` source and restarts the deadline; every sendable state sends; a second
press answers the same meeting and sends nothing; **two simultaneous presses place one bot**
(`peak_in_flight == 1`); a runner tick after a click sends nothing; the hours cap, dedupe (own bot,
another account's bot), capacity, the per-user limit and another live join on the code are each
refused with the right code and **no bot, no row change**; meeting over is 409; suspended is
refused; scheduled, dispatching, cancelled and completed are 409 `cannot_send_now`; another
person's id is 404; a refusing host is 502 and a later press works; a missing template is 409; a meeting that has not started is 409 `not_started` (a future
`skipped / needs_reconnect`, `failed` and `no_capacity` join) and the lists' `can_send_now` equals what
the route accepts, row by row; an unexpected `ValueError` is a 500 that frees the row lock; an orphan
bot of the person's is adopted; the
list holds the right rows for seven days only, never someone else's, names a nameless event by
platform and code and leaves out a dispatched-then-failed join; Upcoming carries the fields; the
mail has the button and the path. Also run green: `tests/test_accounts.py` (route enumeration),
the mail and join suites; `ruff check .`, `ruff format --check .`; `pytest --collect-only` over all of
`tests/`. The race the barrier cannot show is covered by a test that holds a click inside the host's
send and runs the runner meanwhile: the runner finds the row held and does nothing, and one bot is sent
(`test_a_runner_tick_in_the_middle_of_a_send_does_not_place_a_second_bot`). Live captures: see the
guide's verification table. **Not verified:** a real bot in a real
meeting (the host is `FakeVexaHost`), a real mail in a mail client.

## Operate / roll back
Server steps before merge: **none**. Revert the PR to remove the routes and the button (the mail
then has no button again if `SEND_AGAIN_PATH` is set back to `None`). Nothing is stored beyond the
ordinary `scheduled_joins` and `meetings` rows.

## Follow-ups
- A calendar connected while a meeting is already past its first 15 minutes has no join row, so its
  Upcoming "in progress" row has no `join_id` and no Send now (spec 7.8 wanted one). It needs either
  the sync to create a row for it or an event-id based route; not built here.
- The hours-cap refusal from Send now is 403 `hours_cap_reached` (the pasted link's status), while
  other refusals are 409.
- The mail's Send it again opens the Meetings page, not the one meeting (the mail payload carries no meeting
  id). A deep link would need the id added to the payload.

## How
- `web/components/app/use-send-now.ts`: one hook for both lists. Takes the row's `join_id`, ignores a
  second press while a call is out, and on a refusal keeps the row and shows the server's message
  (`errorMessage`; a 404 says "This meeting is no longer on your list."). `meeting_ended`,
  `cannot_send_now`, `account_suspended` and a 404 read the page again (the row changed behind it); busy,
  hours and a host failure leave it as it is.
- `web/components/app/not-recorded.tsx`: the card. Nothing is drawn while there is nothing to show.
- `web/components/app/meetings-calendar.tsx`: wraps `CalendarBand` and `NotRecorded` with one hook and one
  toast, and `router.refresh()` after a success so the new meeting, both lists and the rows follow.
  `web/app/page.tsx` reads `GET /api/not-recorded` next to the calendar (an unreadable list draws nothing).
- `web/components/app/calendar-upcoming.tsx`: the row's note and button; optional `sendNow` prop, so the
  existing tests and the Settings page are untouched.
- `web/lib/api/client.ts`, `types.ts`: `calendar.notRecorded()` and `calendar.sendNow(joinId)`.
- `web/styles/pages.css`: `.cal-up-actions`, `.nr-reason`, `.nr-error`.
- Mock and shots: `web/scripts/mock-api.mjs` (`--notrecorded`, `--sendnow`), `web/scripts/parity-shots.mjs`.

## Verification
`web/tests/not-recorded.test.tsx` (12 tests, on the captured bodies): the card, the rows and the
server's words; nothing drawn when empty; no button for a meeting that is over; no codes in the text;
Send now sends the join id, shows the toast, drops the row and reads the page again; the button is
disabled while the call is out and a second press is ignored; a refusal keeps row and button and shows
the captured words; trying again clears the message; a "meeting over" answer and a 404 read the page
again and say so; the Upcoming row shows the note and the button (and none on other rows) and sends the
join id, not the event id. Also green: `web/tests/calendar-upcoming.test.tsx` (31), lint, typecheck.
**Not verified:** a real browser against the real API (the shots use the mock that replays captures),
a screen reader pass, the Upcoming row's wrapping with a very long reason at 320 px.
