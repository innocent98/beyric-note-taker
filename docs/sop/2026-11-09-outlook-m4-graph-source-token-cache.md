# SOP: Outlook phase O, M4, the Graph source and the rotating token cache

## What shipped
`app/graph_client.py`: `MicrosoftSource` (the `CalendarSource` for provider `microsoft`: a full-window `calendarView` every sync, `get_event`, error mapping) and `MicrosoftTokenCache` (access tokens minted from a refresh token that **rotates on every use**, the new one saved with a compare-and-swap). Plus `app/microsoft_alerts.py` (the admin alerts about our client secret). Branch `feature/outlook-m4-graph-source`, **stacked on `feature/outlook-m3-connect` (PR #152)**, itself stacked on M2 (#150) with M5 (#151) merged in: retarget each base to `main` in order. **No migration.** Dark: the registry builds a `MicrosoftSource` only while `MICROSOFT_CALENDAR_ENABLED` is true, so the scheduler, the sync and the join runner touch nothing Microsoft in production.

## Why
Spec 4.3 and 5.1: Microsoft returns a new refresh token on every refresh (Google never changes it), so an unprotected write would let a slow, stale refresh overwrite a newer token and lock a person out; and the sync must read Graph with the same safety rules as the Google client (no URL from an answer, no token to another host, no body in a log).

## How
| Piece | Decision |
|---|---|
| Sync (D7) | `GET /me/calendarView` for now minus one hour to now plus fourteen days, `$top=250`, the spec's `$select` (the assumed list, no `createdDateTime`/`lastModifiedDateTime`, which do not support `$select`), both `Prefer` values as **two header lines** on every page and on `get_event` (`outlook.timezone="UTC"`, `IdType="ImmutableId"`). Every sync is a full listing: the batch is `complete=True, full=True`, no sync token, so the sync's existing "absent means removed" sweep applies and `_full_due` is simply true. A page failing after the first, an unusable next link or the 40-page cap returns an **incomplete** batch (nothing is cancelled); a failing first page, a revoked grant or a refused token raises |
| `nextLink` rule (review focus 6) | Followed only if it starts with `https://graph.microsoft.com/v1.0/` (`graph_http.under_graph_base`: https, exact host with no userinfo trick, no backslash or control character). Anything else (another host, `http`, `graph.microsoft.com@evil`, a look-alike host, a relative or non-string link) ends the read as incomplete and is **never requested**, so the `Authorization` header cannot go there. The link is requested as given (no parameters added) and carries the `Prefer` lines and the token again |
| URLs | `graph_http.get` refuses any URL not under the Graph base before a request is made; redirects off; no proxy from the environment; a timeout on all four stages (`calendar_http`); an event id is quoted into one path segment (`=`, `/`, `?`, `#`, `%`, space, backslash and non-ASCII all stay in it); `""`, `.` and `..` and non-strings raise before any request |
| Errors | 401: the cached token died early, mint a fresh one and retry once, a second 401 is `AuthRevoked`. 403 with `ErrorAccessDenied` or `Authorization_RequestDenied` is `AuthRevoked` (the grant does not cover the calendar); any other 403, 429, 5xx, 4xx and a malformed or non-JSON page are `TransientError` carrying the status only (never Graph's message). `get_event`: 404 and 410 are `None` ("the source no longer has it"), the rest as above. The 403 code list is documented by experience, not by Microsoft's pages (M0 S6) |
| Rotation (review focus 1) | `_mint` reads the **current** blob from the row in its own short transaction, decrypts it (`ms_refresh_token`, owner the user), calls `MicrosoftOAuth.refresh` on the connection's own tenant, then `UPDATE ... SET refresh_token_enc = :new, key_version = :v WHERE id = :id AND refresh_token_enc = :previous`. A stale writer matches no row: it logs "another writer won" (no token) and the sync carries on with its access token; the old refresh token still works until its own expiry, so a lost write is not an outage. A database or vault error while saving is logged by exception type and also never fails the sync. No new token in the answer means no write. The new token is encrypted under the **current** `TOKEN_ENC_KEY` version (Microsoft rows migrate to a new key by refreshing). The old blob is gone after a swap |
| Cache | Per connection, in memory, tokens held as `vault.Secret`; refreshed five minutes early; concurrent callers for one connection mint once (a lock per connection; tested with eight threads); a transient failure rides a token that still has 30 seconds; `AuthRevoked` drops the cached token; `invalidate` and `forget` like Google's; not picklable, `repr` redacted. A missing key is transient (the user's grant is fine); an undecryptable blob is `RefreshTokenUnreadable`; no token or no tenant is a dead grant |
| Client secret (review focus 10) | `ClientRejected` (our own expired or wrong secret) stays transient for the connection. When Microsoft names the expiry (AADSTS7000222) the admins get one alert a day (`microsoft_alerts.secret_expired`, via `alerts.notify_admins`, deduped by a 24-hour bucket key), from the cache and from the callback (`ClientMisconfigured`). From 30 days before `MICROSOFT_SECRET_EXPIRES_ON` each source sends a reminder once per day per process (`secret_expiring`; the DB dedupe makes a second process harmless). The text names the action, never a secret or a URL. An alert that cannot be written is logged by exception type and never raises |
| Throttling (review focus 9) | A 429 is transient; the sync's pace after any error is unchanged (it retries after `SYNC_EVERY`, not every minute); one connection is read by one call at a time |
| Wiring | The registry row's `make_source` now builds `MicrosoftSource(settings)`; `build_sources`, `register_calendar_sync` (one job per provider: `calendar_sync` and `calendar_sync_microsoft`) and `register_jobs` already hand one registry to the sync and the runner, so they share one cache per provider. No scheduler change |
| Rejected | Delta queries (D7: more states than gain); reading the refresh token from the in-memory `conn` (it can be stale: the row is the truth, and the swap compares against what was read); a row lock around the Microsoft call (a slow Microsoft must never hold a database connection); retrying a 429 inside the sync; a mailbox-missing 404 as `AuthRevoked` (reconnecting would not help; the connection degrades after 30 minutes and says so) |

## Opus review fixes (2026-11-09, review of #153)
- **A deleted Outlook event no longer gets the bot** (the blocker). The join runner's re-check built Google's `{"id","status":"cancelled"}` stub when `get_event` returned None; the Graph parser rejects it, `_parse_all` skipped it as unreadable and nothing was cancelled. The stub is now per provider (`Provider.cancelled_stub`, `calendar_providers.cancelled_stub(provider, id)`; Microsoft's is an id-only cancelled event in Graph's shape that `parse_event` reads as `cancelled`). A **runner test with `MicrosoftSource`** proves a 404 `ErrorItemNotFound` cancels the join and places no bot.
- **`get_event` returns None only for 410 or a 404 whose code is `ErrorItemNotFound`.** Any other 404 (`MailboxNotEnabledForRESTAPI`, `MailboxNotSupportedForRESTAPI`, a bare or HTML 404) is transient; a runner test proves a mailbox-level 404 never cancels a real join.
- **The cached access token is dropped on every `AuthRevoked`** (second 401, grant-code 403, as well as a revoked refresh), and each cached token carries a stamp of the identity it was minted for (`account_subject`, `tenant_id`, `connected_at`): a reconnect over the same row, even as another Microsoft person, can never read with the old token. Tested for the 403, the second 401 and the changed identity. (`calendar_connect.register_token_cache` stays unwired, as before: the web process cannot reach the scheduler's cache, so the stamp is what protects the Microsoft side.)
- **`..` and its encoded forms** (`%2e%2e`, `%2E%2E`, double-encoded, `.` segments) are refused by `under_graph_base` and before any token is minted by `get_event`; a dotted query is fine. Added to the hostile-link table.
- **One Graph call at a time per connection**, across the sync thread and the runner (a lock around each call in the shared source); the docstring now says exactly that. Tested with six threads (never more than one in flight).
- **The secret-expiry reminder has its own hourly job** (`microsoft_secret_reminder`, registered with the Microsoft sync job, daily-deduped) so admins are reminded with no connection due; the in-sync reminder stays.
- `microsoft_oauth._lifetime` is raised to at least ten minutes (`MIN_LIFETIME`), so a tiny `expires_in` cannot cause a refresh and a rotation on every call.
- The log line says "the connection was removed" when the row was deleted during a refresh, "another writer won" only for a real lost race.

## To confirm with the M0 run
1. Both `Prefer` values are honoured together when sent as two header lines (look for `Preference-Applied`; the M0 script sends them comma-joined, so confirm a two-line request too).
2. The `$select` list returns every field the normaliser reads, and `@odata.nextLink` (if it appears at all at `$top=250`) is under `https://graph.microsoft.com/v1.0/`.
3. A real 401 after a refresh, and the 403 codes for a narrowed or blocked grant (`ErrorAccessDenied`? `Authorization_RequestDenied`?) (S6).
4. `ImmutableId` ids really are stable when an event moves, and `GET /me/events/{id}` accepts them quoted into one segment (ids end with `=`).
5. The error answers of the token endpoint for a removed grant, and whether a refresh returns a new refresh token every time (M2's list).

## Operate / roll back
**Server steps before merge: none** while the flag stays false (nothing builds a Microsoft source). **Switch-on needs this PR deployed before the flag**, plus the variables of the M3 SOP and the section 7 gate of the spec. After switch-on watch for `calendar_sync_microsoft` in the scheduler log and for a "not saved (another writer won)" line, which should be rare. Roll back by reverting the PR (then the flag must stay off: M3's registry row would raise at source build time); the refresh tokens already rotated stay valid.
