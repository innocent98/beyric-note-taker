# SOP: Outlook phase O, M1, the provider-neutral foundation

## What shipped
The plumbing that lets a second calendar provider plug in without a parallel code path (spec `docs/superpowers/specs/2026-11-04-outlook-oauth-design.md` sections 6.1 to 6.3): a **provider registry**, neutral account columns, `oauth_flows.provider`, `/api/calendar/{provider}/...` routes, `account_email` and `provider` on `GET /api/calendar`, a **source registry** for the sync loop and the join runner, shared HTTP helpers, and the **one-calendar-at-a-time** rule. Branch `feature/outlook-m1-provider-foundation`, PR to `main` (number in the PR list). Migration **0027**. **No behaviour change for Google**, and nothing Microsoft is reachable: there is no Microsoft row yet, so its routes answer 404. No Outlook wording anywhere.

## Why
Google was wired in by name (`provider == "google"`, `google_*` columns, one `GoogleSource` handed to the sync and the runner). A Microsoft subject stored in a column called `google_sub` is how a later bug (matching the wrong provider) is born, and a second source would have needed a parallel sync and runner. Doing the rename and the registry first, before more tasks (C15b, ICS, Outlook) add references, is cheap now and expensive later.

## How
| Piece | Decision |
|---|---|
| Registry `app/calendar_providers.py` | One `Provider` row per provider: event parser, `granted_features`, `enabled(settings)`, `make_source`, flow cookie name and path. Google is the only row. `ROUTE_PROVIDERS` is the closed set a URL may name. Later tasks add a row and nothing else: M2 to M5 add `microsoft`, C23 adds `ics` |
| Source registry | `SourceRegistry` (provider to source), `as_registry` (accepts a registry, one source, an iterable or nothing, so every existing caller and test keeps working), `build_sources(settings)` (one source per enabled provider, each with its own access-token cache). The scheduler builds it once and hands it to both the sync and the runner, so they still share each cache |
| Sync | `register_calendar_sync` registers **one job per source**; Google's keeps the name `calendar_sync` (others would be `calendar_sync_<provider>`). `_parse_all` picks the parser by `conn.provider` through the registry. `sync_due_connections` is unchanged (it already filtered by `source.provider`) |
| Runner | `run_due_joins` takes the registry. The two-minute re-check asks the source of **its own connection's provider** (`registry.get(conn.provider)`), and with none skips the re-check exactly as before. Same outcome for Google (the old test `conn.provider != calendar.provider` is the same condition) |
| Migration 0027 | Renames `google_account_email`, `google_sub`, `google_hosted_domain` to `account_email`, `account_subject`, `account_domain` (no data moves; `users.google_sub`, the sign-in column, is **not** touched). Adds `tenant_id`, `account_kind` (`personal`/`work`, check), `tenant_domains`. Provider check widened to `google, ics, microsoft`. `oauth_flows.provider` (default `google`, check). Downgrade renames back and drops the new columns; **it fails while a `microsoft` connection exists** (the narrower check cannot hold it): delete those rows first |
| Routes | `POST /api/calendar/{provider}/connect`, `GET .../callback`, `POST .../disconnect`; `provider` is `google` or `microsoft`. The Google URLs are unchanged. `microsoft` answers 404 `calendar_unavailable` until it has a registry row; other names are 422. The Microsoft callback is added to the public routes (`auth.PUBLIC_API`, answers a signed-out visitor itself like Google's) and to the edge test's no-zone list (a redirect, cheap failures; **no nginx change**) |
| Flow isolation | `OAuthFlow.provider` is stored at start; `_take_flow(..., provider)` deletes the state whatever the answer and returns it only if the provider matches, so a Microsoft state can never finish at the Google callback (tested) |
| One calendar (6.3) | `calendar_connect.other_live_calendar`: another provider's connection that is `connected`, `degraded` or `needs_reconnect` **and** gives the calendar feature. Start refuses with 409 `calendar_already_connected`; the callback redirects `?calendar_error=already_connected`. The check runs after locking the user's own row in `_store`, so two tabs finishing two providers queue. A Meet-only Google row, a `disconnected` row and a features request of only `meet` never block. Wired for Google only; the other side arrives with Microsoft |
| API | `GET /api/calendar` has `account_email` and `provider` (`google`, or null when not connected) in place of `google_email`. No compatibility alias: FE and API ship together. `live_calendar_connection` (one function in `calendar_connect`, used by the state and the recurring routes) replaces two copies of "the user's Google connection" |
| Shared HTTP helpers | `app/calendar_http.py` (`client`, `send`, `json_object`, the timeout) lifted out of `gcal_client.py`, which keeps thin Google-named wrappers so its messages ("Google request failed") and every existing test are unchanged |
| Rejected | Keeping `google_*` and adding `ms_*` (that is the parallel path). A compatibility alias for `google_email` (same repo, ships together). Putting the Microsoft feature check in `calendar_connect` (a cycle with the registry: it now lives in the registry and `calendar_connect.granted_features` delegates). Building a Microsoft stub row so the routes exist (they answer 404 correctly without one) |

## Verification
- Tests first for the registry, the 404/422 routes, flow isolation and the one-calendar rule (`tests/test_calendar_providers.py`, 22 cases, using a stand-in `microsoft` registry row), then the full suite once (this touches `join_runner.py`, `scheduler.py` and `gcal_sync.py`, the live join path): result in the PR body.
- Google paths re-run by the existing suites, unchanged apart from names: connect and callback (all seven checks, reconnect, different account, Meet upgrade), disconnect (revoke, hooks, deletions), `GET /api/calendar` and the settings/override writes, recurring, the sync (full and incremental, errors, 410), the join runner (placement, re-check, dispatch) and the end-to-end fake-clock test (fake Google, sync, scheduler, runner, fake Vexa host).
- Migration 0027 round trip on a scratch Postgres: values kept under the new names, flows default to `google`, a Microsoft row accepted, bad `account_kind` and flow provider rejected, downgrade refused with a Microsoft row, then restored.
- `GET /api/calendar` captures: a fresh run of `scripts/capture_calendar_state.py`, `capture_calendar_settings.py` and `capture_calendar_connect.py` on 2026-11-05 returned `account_email` and `provider` next to each other. The committed capture files were then **renamed in place** (not regenerated) because the web tests pin their timestamps and texts; the fresh run showed the only differences were the field names and times. Honest note: the older captures also predate `auto_join_paused`, which the guide's snippets do not show.
- Not verified live: nothing Microsoft exists to verify; 409 and `already_connected` are tested only.

## Operate / roll back
- **Server steps before merge: none.** No new `.env` variable, no nginx change. The deploy runs migration 0027 (renames and one added column set, fast; Google's rows keep their values). After deploy: server head 0027, `/health` 200, one Google calendar sync still ticking (`calendar_sync` job).
- **Roll back** by reverting the PR and `alembic downgrade 0026` (tested; refuses only if a `microsoft` row exists, which cannot exist before M3). The old code reads `google_*`, so the code and the migration must go back together.

## Follow-ups
- M2 to M5 add the `microsoft` row (parser, features, source, flow cookie `calendar_flow_ms`), the OAuth client and the Graph source; the registry already routes everything to it.
- `GET /api/calendar` still requires the Google client (`_enabled`) to answer. When Microsoft can be on while Google is off, that check becomes per provider (M3/M6).
- `register_token_cache` (drop the cache on disconnect) is only wired in tests; the web process cannot reach the scheduler's cache. Pre-existing, untouched.
