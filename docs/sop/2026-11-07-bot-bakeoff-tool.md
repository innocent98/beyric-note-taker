# SOP: bot bake-off tool (Vexa vs Skribby vs Recall)

## What shipped
A local command-line tool, `tools/bakeoff/bakeoff.py`, that sends a Skribby or Recall bot into a Google Meet, records what happens (admitted, knocked, refused, never joined), asks the vendor to make the bot leave after about a minute, and logs one CSV line per trial; plus a `note` command for our own Vexa bot and a `report` command. PR: branch `feature/bot-bakeoff-tool` (number in the PR). **Not run against a live vendor** (no keys existed); the owner's first live check is in `tools/bakeoff/README.md` step 4. No FE guide: no API change.

## Why
Google refuses our anonymous Vexa bot about a quarter of the time. The 2026-11-06 research (`docs/spike/meeting-bot-vendors.md`) found that no vendor publishes a Meet join-success rate, so the owner decided on 2026-11-07 to measure it: the same kind of real calls, one arm per bot, counting admissions, knocks and refusals. Skribby's Free plan (5 bot hours a month) and Recall's first 5 hours are free, so the test costs nothing if the hours are watched.

## How (decisions and rejected alternatives)
| Decision | Why |
|---|---|
| One file, Python standard library only (`urllib`, `csv`, `argparse`), works on Python 3.9 (macOS's own `python3`) and 3.12+ | Nothing to install on the owner's Mac. Checked: `--dry-run` runs under `/usr/bin/python3` 3.9.6. Rejected: `requests`, `httpx` (an install for no gain). |
| One bot per meeting; plain different names ("Ada W" Skribby guest, "Sam K" Recall guest) | Recall's bot-detection page matches names like "notetaker", "recorder", "assistant" and makes bots leave; two bots in one call could remove each other. The signed-in Skribby bot shows the account's own name (its page says `bot_name` is ignored). |
| Seconds come from the **vendor's own timestamps** (Skribby `events[].created_at` from the bot's `created_at`; Recall `status_changes[].created_at` from `joining_call`), not from when we polled | A 5 or 10 second poll cannot distort "seconds to admission", and the Mac's clock cannot skew it. Our own clock is only used for the stay timer and the lobby limit. Fallback to our clock only if a timestamp is missing. |
| **Skribby knocks are inferred, Recall knocks are observed** | Skribby's lifecycle page says `joining` "includes the Waiting Room phase" and there is no lobby status; Recall has `in_waiting_room`. For Skribby, 20 seconds or more in `joining` before `recording` counts as a knock (`--knock-threshold`); the note on every such row says "inferred, not observed". `seconds_to_lobby` is therefore Recall-only. |
| Results: `admitted`, `knocked-then-admitted`, `refused`, `never-joined`, plus `error` | `error` is our side or the vendor's API (a refused create, bad credentials, internal failure, an unknown fatal code). It is listed in the report but kept out of the admitted percentage, so a bad key cannot make a vendor look like Google refused it. Unknown Recall fatal codes land in `error` on purpose (the page says codes may be added without notice). |
| Refusal mapping | Skribby: `not_admitted/request_denied`, `bot_detected` (only after it stops retrying), `auth_required`. Recall fatal: `google_meet_bot_blocked`, `google_meet_knocking_disabled`, `google_meet_organisation_restricted`, `google_meet_sign_in_missing_login_credentials`, `meeting_requires_sign_in`, `meeting_locked`; call-ended `bot_kicked_from_waiting_room`. Lobby timeouts (`waiting_room_timeout`, `timeout_exceeded_waiting_room`) and our own stop in the lobby are `never-joined`. |
| `bot_detected` is not treated as final at first sight | The bot-detection page says Skribby retries up to 3 times with new IPs and may toggle with `booting`. The tool waits until four `bot_detected` events or 90 seconds unchanged. A bot that recovers is logged `admitted` with "bot_detected xN (Skribby retried)" in the notes. |
| Polling: 5 s (Skribby), 10 s (Recall); 429 waits for `Retry-After`; 409/502/503/504/507 retried a few times; network errors back off 2, 4, 8 s; 403 is never retried | Skribby's docs say a concurrency 403 creates no bot and must be retried deliberately; Recall's 507 asks for a retry after about 30 s. |
| Trial ends: about `--stay` (60 s) after admission, or on failure, or at `--lobby-limit` (600 s) at the door; Ctrl-C and any crash also ask the vendor to leave | Saves free hours and never leaves a bot running. A vendor-side safety net too: Skribby `stop_options.time_limit` and `waiting_room_timeout`, Recall `automatic_leave.waiting_room_timeout`. |
| Budget guard: sums `bot_minutes` per vendor from the CSV; refuses a new trial at 4.5 h (`--cap-hours`, env `BAKEOFF_CAP_HOURS`, `--force`, `--budget-since DATE`) | The free allowances are 5 h; the 0.5 h margin covers a trial that is already running (at most about 11 minutes). Skribby's 5 h renews monthly, hence `--budget-since`. The count is conservative (whole minutes for Skribby; fatal and lobby time counted although the vendors may not bill them). |
| Recall request keeps nothing: `recording_config` = audio only, no transcript, retention timed 1 hour | New Recall accounts keep media forever by default (earlier note); these are throwaway test calls. Field shapes checked in the saved OpenAPI excerpt. |
| Keys: environment first, then `~/.config/beyric-bakeoff/keys.env`; never printed or logged; `Authorization` redacted in `--dry-run`; vendor error text is scrubbed of the key and of `Bearer ...` strings; `RECALL_REGION` must be one of the four known regions | The region check also means the key cannot be sent to a mistyped or hostile host. Skribby's host is fixed (`platform.skribby.io`, or `platform-jp.skribby.io` with `SKRIBBY_REGION=jp`). |
| Log: append-only CSV, columns `time_utc, time_lagos, trial_id, arm, host_type, meeting_code, result, seconds_to_lobby, seconds_to_admission, final_status, bot_minutes, notes`; the code keeps only its last 4 letters (dashes removed) | The spec said "last 4 chars"; without the dashes the cell never starts with `-` (a spreadsheet would read that as a formula). |
| Skribby transcription model defaults to `none` | The trial only measures joining. The models page lists `none` as "No Transcription"; the Free plan lists "Audio Only". Whether they are the same is **not verified**; `--skribby-model groq/whisper-large-v3-turbo` is the fallback. |

## Where the raw pages disagree with the second-hand notes (the page wins)
Pages saved in `docs/spike/primary-pages-2026-11-07/`.
| Topic | Second-hand note | Raw page | Effect |
|---|---|---|---|
| Polling Recall for status | `recall-api-reference-read.md`: docs "do not recommend" it | The Retrieve Bot page says polling for status changes "is an anti-pattern and must not be used in production integrations" (limit 300 requests a minute per workspace) | Fine for a local test with no public webhook address; polling is gentle (10 s). A production adapter must use webhooks. |
| `google_meet.login_required` | "not documented anywhere I read" | Documented in the Google Meet FAQ ("Can I enable authenticated Google Meet bots for some meetings...": absent means sign in only if the meeting requires it; `true` means always) though not in the Create Bot schema | Out of scope here (no signed-in Recall arm); noted for the signed-in decision. |
| Recall region for pay-as-you-go | A search snippet said pay-as-you-go should use us-west-2 (page 404, not verified) | The regions page marks all four regions pay-as-you-go; sign-up links exist for US West, EU and Asia only; `api.recall.ai` is the same as us-east-1 | README tells the owner to use the region of the sign-up link he used. |
| Recall auth header | Two pages "disagree slightly" | The authentication page says the `Token` prefix is optional | Tool sends `Token <key>` (the form in the guides). |
| Recall billing | "from joining_call to a terminal event" | Same, and `fatal` bots are not billed; waiting-room time is billed | Matches; the tool counts fatal time anyway (conservative). |
| Skribby lobby | The earlier summary spoke of knocks as if visible | No waiting-room status; the lobby is inside `joining` | Knock is inferred for Skribby (above). |
| Skribby authenticated bot on the Free plan | "Easiest signed-in setup", free tier 5 h | The pages never say Authenticated Accounts are available on Free | Flagged in the README; first live check of `skribby-auth` answers it. |

## What's involved
`tools/bakeoff/bakeoff.py` (the tool), `tools/bakeoff/README.md` (owner's steps), `tests/test_bakeoff_tool.py` (61 tests), `docs/spike/primary-pages-2026-11-07/` (32 saved pages and a README), `.gitignore` (`tools/bakeoff/logs/`, `tools/bakeoff/*.env`), `docs/checklist/master-checklist.md`. Nothing under `app/`, `web/`, `alembic/`, no migration, no new dependency, no `.env` variable on the server, no nginx change.

## Verification
- `ruff check .` and `ruff format --check .` with the pinned ruff 0.17.3: clean.
- `PYTHONPATH=. pytest tests/test_bakeoff_tool.py`: 61 passed, no database. Fake vendors answer in the shapes of the raw pages. Covered: status mapping per vendor (admitted, quick vs knocked, waiting room, refused, lobby timeout, bot_detected retry and recovery, unknown fatal codes), seconds arithmetic from vendor timestamps (including `Z` and 7-digit fractions), whole trials (stay then leave, lobby limit, Ctrl-C, failed create), 429 `Retry-After`, 507 and network back-off, budget guard (per vendor, `--force`, `--budget-since`, env cap), log columns and append-only, `note`, `report` numbers and the plain-words line, `--dry-run` (nothing sent, nothing logged, no key shown, works without keys), redaction of keys echoed back by a vendor, key file parsing, region and Meet-link validation. One test opens a socket to a throwaway server on this computer to exercise the real HTTP code.
- `--dry-run` also run under macOS's `/usr/bin/python3` 3.9.6.
- **Not verified:** any live vendor call. Specifically: the real create and status JSON (field names come from the raw reference pages; the `event` name inside Skribby's `events[]` is blank on the page and is not read by the tool); whether Recall `leave_call` works while the bot is in the waiting room (if not, `automatic_leave.waiting_room_timeout` still ends it at the same limit); whether Skribby's `none` model and authenticated accounts work on the Free plan; the Skribby knock threshold of 20 s (a guess to tune after the first runs); and the manual Vexa `note` (typed by hand, as accurate as the owner's stopwatch). No call is made to notes.beyrictech.com and nothing reads production.

## Operate / roll back
Run it from the owner's Mac (README). Nothing to deploy. CI on a PR that touches `tests/` runs the Python suite; a merge of this PR to `main` triggers the `deploy` workflow (it runs after every green `ci` push to main, with no path filter), but the Docker image copies only `pyproject.toml`, `app/`, `alembic/`, `alembic.ini` and `scripts/` (`Dockerfile` lines 12 to 18), so the images are unchanged and `docker compose up -d` should not restart the bot worker (inferred from the Dockerfile; not tested). Roll back: delete `tools/bakeoff/`, the test file and the `.gitignore` lines; the log file is local.

## Follow-ups
- Run the first live check, then tune: knock threshold, default poll, whether `none` works.
- If the bake-off picks a vendor, a production adapter needs webhooks (not polling), signature checks and the transcript shape, none of which this tool touches.
- Signed-in Recall (needs a Google Workspace with Legacy SSO) is out of scope; add an arm only if the decision needs it.
- A Vexa arm that reads our own bot status automatically would need a call into the app, which this tool deliberately does not make.
