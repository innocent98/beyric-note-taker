# SOP: W3 Team, backend (PR 1 of 2)

## What shipped
Invitations to a team (hashed single-use link, 7 days, resend, revoke), joining as a new person (reserves a pilot place, bypasses a closed or full pilot for that address) or as an existing account (their team of one dissolves into the one they join), roles with `403 team_forbidden`, remove and leave, per-meeting share and unshare, the team default `share_new_meetings`, alias editing, the "Team invite" mail, the account-deletion rule for team owners, and the route-enumeration tests. Backend only: the screens are PR 2 (`feature/w3-team-screens`), stacked on this one. Migration **0026**. Branch `feature/w3-team-backend`. PR: see the PR page (not merged).

## Why
Spec sections 2 (rows 1, 2, 4, 5, 19), 4, 6.1, 8.1 to 8.4, decisions D1 to D3. W0.4 gave every account a team of one and `visible_meetings(user)`; W2 made tasks that name teammates. Without invites there was nobody to name, and the rule "a meeting is private unless shared" had no way to be shared. The risky parts are permissions (who sees a meeting), tokens (an invite link joins a team) and slot reservation (an invite lets someone in past a closed pilot), so each is one function with its own tests.

## How: the decisions
| Topic | Decision | Alternatives rejected |
|---|---|---|
| Token | `team_invites.token_hash` = SHA-256 of a 32-byte random token (`tokens.mint`, `tokens.digest`); raw token only in the mail payload (scrubbed once sent, like every link template). Single use is one `UPDATE ... WHERE accepted_at is null AND live ... RETURNING`, so two requests cannot both win. Resend replaces the hash (the old link dies) | Reusing `auth_tokens` (its purpose enum and user binding do not fit: an invite belongs to a team and an address, not to a user) |
| Slot reservation (D2) | **No counter.** `signup.slots_taken` now adds `team_invites.reserving_count`: distinct addresses with a live invite that are not already counted (a confirmed account, an account from a waiting-list invite, a live waiting-list invite). Revoke, expiry or accept change the number by themselves, so it cannot drift. Invite creation answers 409 `pilot_full` for an address with no account when `has_room` is false | A reserved-slots column (drifts); reserving for existing accounts (they already are accounts) |
| New person | `POST /api/signup` takes the link as `invite_token` (same field as a waiting-list invite): it bypasses `closed` and `full` for its own address only, claims the invite on the new row, and `verify_email` joins the team when the address is confirmed (same transaction, under the sign-up lock). Google: a live invite for the verified address is used the same way. `may_confirm` treats a live team invite as a reserved place | A second sign-up route; joining at sign-up (the mailbox is not proved yet) |
| Existing account | `POST /api/team/invites/accept` while signed in as the invited address; `teams.join` dissolves their team of one: tasks move, `shared_team_id` of their meetings is cleared, invites they sent die with the old team (FK cascade). Someone on a team with other people gets 409 `already_on_team` and the link is not used up. Both teams are row-locked lowest id first so two people accepting each other's invites cannot deadlock or strand a member | Merging two real teams (no spec for it) |
| One answer for a bad link | wrong, used, expired, revoked and "someone else's address" are all `400 invite_invalid` | distinct messages (they tell a stranger which links were real) |
| Account existence | invite results never say whether an address has an account (same `sent` and shape); `pilot_full` only appears when there is no free place AND the address has no account (an unavoidable tell, to the inviting admin only) | |
| Roles | owner: all; admin: invite members (not admins), remove members (not admins/owner), team settings, any alias; member: own aliases, leave. Role changes: owner only. Owner cannot be removed or leave while others remain (409 `owner_cannot_leave`) | Letting admins invite admins (privilege growth without the owner's say) |
| Ids | a member is addressed by `user_id` (what tasks use), an invite by its own id; anything not on the caller's own team is 404 before any permission is checked | |
| Remove / leave | `teams.leave`: open tasks assigned to them unassigned; **tasks read from their own meetings move with them to their new team** (assignee kept only if it is them, since the old team can no longer read those meetings); their shared meetings unshared; invites they sent revoked; fresh team of one. `tasks.visible` now requires the assignee clause to match the task's team, so a done task that still names an ex-member gives them no window | Leaving tasks of a private meeting in the old team (orphans nobody can read) |
| Share default (D3) | `teams.apply_share_default` runs once, when notes are first written (`pipeline._step_notes`, only when `meetings.notes` was empty), never at join time and never on a rewrite. It covers meetings of the team's **owner and admins only**: an admin switching it on must not publish a member's calls. **Decision for the lead to confirm:** the spec says "team default" without this limit | Applying it to every member (silent publishing of someone else's calls) |
| Share switch | `POST/DELETE /api/meetings/{id}/share`, owner only (404 for anyone else), idempotent, return the meeting. `MeetingDetail` gains `shared_with_team`, `can_share`, `shared_by` | Sharing from the team side (an admin could publish another person's meeting) |
| Aliases | `PATCH /api/team/members/{user_id}` `aliases` replaces the list, cleaned (one line, 60 chars, de-duplicated by matching form, max 20); owner/admin anyone's, member their own. Owner matching already read only **active members** (`tasks.members_of`), so invited people and suspended accounts never match | |
| Deleting an account | `admin.schedule_deletion` and `scripts/delete_user.py` refuse (409 `team_owner_has_members`) for an owner of a team with other members; `scripts/transfer_team_owner.py <team id> <email>` (new) hands it over. `teams.remove_users` keeps its hand-to-the-earliest fallback so a forced purge is never blocked. Invitations addressed to a purged account are deleted | |
| Limits | at most 10 open invitations per team and 20 created per 24 h (409 `invite_limit`); resend needs a minute since the last mail (429 `too_soon`); account-style mail, so not counted against the daily notes caps | |
| Preview route | `GET /api/team/invites/preview?token=` is **public** (the 256-bit token in the query is the credential) so the invite page can say who invited you and send a visitor to sign in or sign up. It tells the holder `has_account` for the address the link was sent to. Added to `auth.PUBLIC_API` and the public list in `tests/test_api.py` | Making the page guess (it would send existing accounts to a sign-up that answers "already registered") |
| Mail | "Team invite" built from the designer's `Emails.dc.html` (heading naming the inviter, one sentence, **Accept invite**, the 7-day line). The inviter's name is used only when it is plainly a name (`PLAIN_NAME`, as the greeting is), else "You have been invited to join a team"; the footer is the standard signature with Beyrichq LTD (spec row 18) | |

## Operate / roll back
- **Deploy:** migration 0026 runs with the app (adds a column with a default and a new table; no data change). Nothing to backfill.
- **Server steps before merge:** none. No new environment variables. Confirm `alembic heads` shows one head (`0026`).
- **Roll back:** `alembic downgrade 0025` drops `team_invites` and `teams.share_new_meetings`; meetings keep their `shared_team_id` (set by the share switch), so teammates would keep reading them after a code rollback to W0.4 (the W0.4 code reads that column already). Revoke by `update meetings set shared_team_id = null` if sharing must stop.
- Hand a team to someone before deleting its owner: `docker compose exec web python scripts/transfer_team_owner.py <team id> <new owner email>`.
