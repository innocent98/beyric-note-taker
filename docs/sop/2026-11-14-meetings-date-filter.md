# SOP: a date filter on the Meetings list

**What shipped.** `GET /api/meetings` takes optional `from` and `to` (`YYYY-MM-DD`), and the Meetings page has a compact filter above the list: From and To date boxes with Apply, quick ranges Today, Last 7 days and Last 30 days, and Clear. The range lives in the address (`/?from=2026-11-01&to=2026-11-07`), so a filtered view can be reloaded and shared. Branch `feature/meetings-date-filter`, based on `main` (an earlier version was stacked on a dashboard-move PR that the owner dropped; the dashboard stays at `/`). **Lead-designed:** the designer's files have no filter, so it is built only from the existing `Card`, `Field`, `Button` and `Alert` styles (one small CSS rule, below). No migration.

## Why

The list shows the newest 50 and pages back with "Show older meetings"; finding "the call last Tuesday" meant paging blind. Adebayo asked for a date filter.

## How

| Piece | What and why |
|---|---|
| Parameters | `from` and `to` on `GET /api/meetings` (`app/api.py`), read as text and parsed by `services.parse_day`: exactly `YYYY-MM-DD`, a real day, year 1900 to 2200. Text, not a pydantic `date`, because `date` also accepts a timestamp or a number of seconds and its messages are not plain. Blank (`?from=&to=`) means none |
| Whose days | The caller's stored time zone (`UserSettings.time_zone`, migration 0018; UTC when none): `services.day_range_utc` turns "first day" and "the day after the last day" into two UTC instants in that zone (`timezones.zone`, zoneinfo), so both days are whole and a clock-change day is 23 or 25 hours long, not a bug. The reader's zone, not the recorder's: a teammate reading a shared meeting sees their own days, the same as the day headings |
| The filter | Inside `services.list_meetings`, added as two `where` clauses on `Meeting.created_at` (the timestamp the list and the headings use) **after** `visibility.visible_meetings(user)`, so it can only narrow what is visible. `before_id` paging, `has_more` and `next_before_id` are untouched: they page by id over the filtered rows (`limit + 1` rows are read, as before) |
| Errors | 422 `invalid_date` ("From is not a date. Write it as YYYY-MM-DD, for example 2026-11-14.", or "To ..."), 422 `invalid_date_range` ("From must be on or before To. Swap the two dates."), through the existing `Refused` handler. Declared on the route so `docs/openapi.json` lists them |
| Page | `app/page.tsx` (`HomePage`, the signed-in dashboard at `/`) reads `searchParams` through `lib/date-range.ts` `readRange` (a damaged value is ignored with a notice line and the full list shown, never an error page), asks the API for the range, and passes `range` to `MeetingList`. "A bot is already on a meeting" is decided from the 10 newest meetings (one extra call only while a filter is on), because a filtered first page may not hold the busy one |
| Filter box | `components/app/meeting-filter.tsx`: a plain `<form noValidate>` (Enter applies, no half-typed date is ever applied), labelled From and To `type="date"` boxes, Apply, the three quick buttons and Clear (shown only while something is set or filled). Quick ranges are computed in the owner's display zone: Last 7 days is today and the six before, Last 30 days today and the 29 before. From after To shows "From must be on or before To." and changes nothing. Applying is `router.push(`${basePath}?...`, { scroll: false })`, where `basePath` is a prop of the list (`/` today), so the filter moves with the page if the dashboard ever gets its own address |
| List | `components/app/meeting-list.tsx`: heading "Meetings on Sat 14 Nov", "Meetings from Mon 9 Nov to Thu 12 Nov", "Meetings from ..." or "Meetings up to ..." (year only when not this year) in place of "Recent"; empty state "No meetings in this range." with the filter still there; the day headings are unchanged; "Show older meetings" asks with the same `from` and `to`; older pages are kept per range (state is keyed by the range, so another range starts again from the server's first page with no effect needed); the periodic and focus refresh is `router.refresh()`, which re-renders the same address, so the filter stays. The filter box is not drawn for an account with no meetings at all and no filter, so the first-run page is unchanged |
| Rejected | Applying on every change of a date box (a date input says "" while half edited, so clearing one segment would clear the filter and the page would reload under the cursor); a separate "last N days" API parameter (the page can compute days itself and the API stays two plain dates); hiding the filter inside a menu (the brief wanted it above the list) |
| Decision where the brief was silent | An explicit **Apply** button is added next to the date boxes (the brief listed none): without it a keyboard or phone user has no safe moment to apply two dates |

## Verification

On the Mac, bounded: `ruff check` and `ruff format --check` (0.17.3), `export_openapi.py --check`, `eslint` and `tsc --noEmit`, `pytest tests/test_meetings_date_filter.py tests/test_api.py tests/test_team_visibility.py -k ...` on a scratch Postgres 17, `vitest run` on `date-range`, `meetings-date-filter`, `meeting-list-days`, `screens`, `meetings-calendar`, `meetings-recurring`. **Live:** `capture_meetings_date_filter.py` ran the real migrations and the real app under uvicorn (Vexa and OpenAI faked; the six meetings are inserted by SQL) and saved the 17 exchanges the guide pastes verbatim. **Looked at in a browser:** `next dev` with `web/scripts/mock-api.mjs` in the in-app browser (the mock ignores `from` and `to`, so only the page, not the filtering, was seen): the box and the quick ranges at desktop width and at 375px (no horizontal scroll, 44px controls), Last 7 days changing the address to `?from=2026-11-08&to=2026-11-14` and the heading naming it. That showed the count ("7 meetings") wrapping beside a long heading on a phone, fixed with one rule in `styles/components.css` (`.card-head .meta` does not wrap or shrink). **Not verified:** the filtered results against the real server in a browser, a day that starts at a clock change against a real Postgres time zone database beyond the unit test, and the effect on a very large meetings table (the existing `ix_meetings_owner_user_id (owner_user_id, id)` serves the owner's rows; `created_at` is not indexed, so a range scan reads that owner's rows: fine at pilot size).

## Operate / roll back

Nothing to run. Revert the PR: the parameters disappear (an old link with `from`/`to` then lists everything) and the box with them.

## Follow-ups

- If a range filter is used heavily on a large table, add an index on `(owner_user_id, created_at)`.
- The filter does not search by title or status; that is a different feature.
- Whether to remember the last range per owner was not asked for and is not done.
