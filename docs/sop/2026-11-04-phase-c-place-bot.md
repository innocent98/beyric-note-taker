# SOP: `place_bot()`, the one place a bot is sent (Phase C, task C11)

## What shipped
`app/placement.py`: `PlacementRequest`, `PlacementRefused` and `place_bot(session, vexa, req, *, now)`, plus `reserve_slot` (the lock and the four checks, used by the retry path). The pasted-link path (`services.create_meeting`, which the Jinja form, the JSON API and the PWA share target all reach) and the "send a new bot to a refused meeting" retry now go through it. `NEW_MEETING_LOCK` and the `bot_already_active` answer are gone. A full note taker answers the neutral **409 `bot_busy`**. Branch `feature/c11-place-bot`, PR 63. No calendar join calls it yet: **C12 (the join runner) is the first caller after the pasted link.** **Dispatcher locking: wants the Opus review before merge.**

## Why
Spec 9.4: one function must be the only place a bot is sent, so the rules about how many bots may run, and for whom, exist once. Before it, the rules lived inline in `_create_meeting` and again in the retry path, behind a single global lock, and a user's own running meeting was named as theirs while another user's was "busy". C12 needs the same checks for a calendar join, and a calendar join cannot ask a person to press the button again, so the refusal has to be a code the runner can act on.

## How
| Piece | Decision |
|---|---|
| Pre-flight order | Hours gate (`usage.effective_cap` and `usage.hours_used`, the same functions as before), per-user limit, duplicate, capacity. A test walks all four with everything wrong at once and then removes the faults one by one. The user's calendar connection is **the caller's** check: a pasted link has no connection |
| Codes | `hours_cap_reached` (403, `PlacementRefused.cap_seconds` carries the cap for the words), `user_limit`, `already_in_meeting`, `meeting_has_note_taker`, `bot_busy` (all 409). `place_bot` raises `PlacementRefused` for these and lets a failed send raise `VexaError`; `services` turns them into `Refused` (`placement_refusal`, and `bot_send_failed` 502). A caller bug (unknown user, a template that is not the user's, an unknown `source`) is a `ValueError` before anything is sent, never a refusal |
| Lock | `pg_try_advisory_xact_lock(PLACEMENT_LOCK = 6004, 1)`, taken **first**, before any check, and held across `send_bot` until the meeting row is committed. The second int is the host id, always 1 until D4. Because the lock is taken before the checks, a request reads the capacity only after every earlier placement has committed (READ COMMITTED gives each statement a fresh snapshot), so two requests can never both see the one free slot |
| A short, polite wait for the lock (Opus review findings 1 and B) | The first version waited up to 35 s inside Postgres, holding a pooled connection (pool 5 + 10 overflow) and an open transaction for as long as the holder's send: about fifteen parallel pastes could have starved every other endpoint. The second version never waited, so while any send was in flight (up to 30 s) everyone got "busy" even with room. Now a request **polls the try-lock for at most `LOCK_WAIT_SECONDS` (3 s)** and rolls back between looks, so its connection goes back to the pool while it sleeps. If the lock is still taken it answers `bot_busy` with `slot_locked` set and the words "A note taker is being set up for another meeting. Try again in a minute."; if the slot is simply full it is the old "The note taker is busy right now. Try again in a few minutes." (same code, two texts, no user, no meeting id). A caller that holds a row lock (the retry path) passes `wait_seconds=0`, because the rollback would drop its lock. The holder is bounded too: `VexaClient.send_bot` has a **total** deadline (`app.vexa.SEND_DEADLINE_SECONDS`, 30 s, a worker thread the caller stops waiting for, because httpx's timeout is per phase and a trickling host never trips it) and a 5 s connect timeout |
| Send failure | `VexaError` is raised **after a rollback**: no meeting row, lock released, the slot is free for the next request (a test places a bot straight after a failed send). A plain `VexaError` (Vexa answered with an error status) never triggers a stop: there is no bot |
| A send that may have worked: keep the code, let the worker settle it (findings 2 and High) | `VexaSendUncertain`: a timeout after the request went out, a broken connection, the deadline, **any 5xx** (a gateway can time out after the bot manager acted), or a success body we could not read. **Not** a connection that was never made (`ConnectError`, `ConnectTimeout`), and not a 4xx other than 409: those are a clear no (plain `VexaError`, no stop, no placeholder). Vexa keeps handling a request the client has left, so the bot can join seconds later and a stop sent now would find nothing (a 404 counts as stopped), leaving an unrecorded bot. So the meeting is kept as a **placeholder**: `bot_sent`, no Vexa id, `completion_reason = SEND_UNCONFIRMED` (the owner reads "Starting the bot"), counted for capacity and the duplicate checks, so the code stays taken (the owner's repeat paste says `already_in_meeting`, a stranger's `meeting_has_note_taker`). The pasted link returns this meeting (201) instead of a 502. **The worker settles it** (`pipeline._settle_unconfirmed`, first thing in `_poll`): if Vexa shows a bot in a **live** state for the code **with its Vexa id** it is adopted and **pinned to that id** (`VexaMeeting.vexa_id`, read from the body's `id`; from then on the worker looks it up by id, never by code, so a reused code cannot hand it another recording; a live bot without an id is not adopted); a finished Vexa meeting on a reused code is not ours and is never adopted; after `UNCONFIRMED_GRACE` (60 s, **counted from the uncertain send**: `send_again` resets `started_polling_at`, so a refused meeting sent again hours later gets the full grace) with nothing the code gets a last stop (guarded by `may_stop_bot`) and the meeting fails with "The bot could not be confirmed in the meeting, so this meeting was not recorded. Please send the bot again." (retry block `no_audio`: the owner pastes the link again). The retry path (`pipeline.send_again`, also used by the worker's automatic resend) does the same. **Cancel is refused while the row is a placeholder** (`can_cancel` is false, so the page does not offer it; the call answers 409 `bot_starting`, "The bot is still starting, so it can't be cancelled yet. Try again in a minute, once it has joined."): a stop by code would find nothing (a 404 counts as stopped), the row would fail, the code would be freed and the late bot would join with no row. End is not offered either (`not_endable`). Rejected: recording a "cancel requested" for the worker to act on (needs a new state and designed copy). **Design gap:** the designer's files have no "cannot cancel yet" state; the button is simply hidden and the error text above is the only wording, so ask the designer for it. **Adoption is stricter (second review):** `stopping` is not adoptable (a cancelled meeting's leftover bot reads `stopping`), and a Vexa id that any other meeting row already holds is never adopted, so a placeholder cannot take over a cancelled meeting's bot or recording. **The grace counts from after the send** (`started_polling_at` is set to the real time after the send, not the caller's earlier `now`, which was taken before the lock wait and the 30 s send) Rejected: having the abandoned request thread stop the bot when it finally returns (does not cover a ReadTimeout, where nothing ever returns, and a stop by code later could hit someone else's bot on a freed code) |
| Saving fails after a successful send | A flush failure: stop the bot (lock still held), roll back, re-raise the **original** error (a failing stop is logged by exception type and never hides it). A commit failure (`placement.commit_or_stop`, used by the retry path as well, finding 4): roll back, then look for a row that points at the new bot id; **if it landed after all** (a lost answer to a commit that succeeded) the bot is a recorded one and is left alone, otherwise it is stopped. If the check itself fails the bot is stopped (an unrecorded bot is worse). The stop is by code and the lock is gone after a failed commit, so it **takes the placement lock again and skips the stop if a live meeting of anyone holds the code by then** (`_stop_if_the_code_is_free`; if the lock or the check cannot be had, the database is failing and nobody else is placing, so it stops) |
| One bot per meeting code, across users (finding 3, the lead's decision after the Opus review) | **This replaces the earlier decision "two accounts in one meeting each get a bot", which is NOT true with one shared Vexa key:** Vexa keeps one bot per meeting code, and `stop_bot` is keyed by platform and code alone. Pre-flight therefore refuses a second user with the new neutral **409 `meeting_has_note_taker`** ("A note taker is already in this meeting.": no user, no meeting id, no hint of who), and a Vexa duplicate refusal at send time (`VexaDuplicateBot`, HTTP 409 **assumed**, not yet captured from a live host) maps to the same refusal and **stops nothing** (the bot there is not ours). The user's own repeat is still the more helpful `already_in_meeting`. Sharing a meeting between accounts waits for C12 or per-user Vexa keys. This is the plan's `..._other_user_is_already_in_meeting`, with a neutral code |
| Stopping only our own bot (finding 3) | `placement.may_stop_bot(session, meeting)`: a stop by code runs only if no other live meeting row on the code is newer (or, when the meeting is not live itself, if there is none at all). Applied in Cancel and End (`services._stop_bot_or_refuse`: a skipped stop still ends the user's row, since their bot is already gone), the worker's refusal handling (`pipeline._stop_bot`) and the user-deletion purge (`deletion.py`, two sites). Without it, user A's stale `bot_sent` row could take out user B's bot after Vexa let B in |
| What counts as a live bot | For the per-user limit and the host's capacity: `bot_sent` **and** `processing`, exactly as `ACTIVE` did before (a meeting being transcribed still holds the slot). For the duplicate checks only `bot_sent`: once the bot has left, the same recurring code is free. **Kept on purpose (reviewer's finding 6, see follow-ups):** the worker handles one meeting at a time and holds it through minutes of transcription, so a new live bot beside a long transcription would sit unseen as "Checking on the bot..." (`docs/sop/2026-11-03-bot-end-controls.md`). Counting `bot_sent` alone (spec 9.4 step 3) needs worker concurrency (D9a) first, and changes what the production box does, so it is not done here |
| Retry of a refused meeting | Now uses `reserve_slot`, so it takes the same lock and runs the same four checks (it used to share only the old lock). Order changed to **row lock first, then placement lock** (`_lock_meeting`, which has its own 10 s bound and answers `meeting_busy`), so nothing ever waits for a row while holding the placement lock |
| No queue | A refusal is an answer, never a queued request: a queued meeting is an unrecorded meeting (decision 2026-11-03). C12's bounded retry until the deadline is the runner's job, not this function's |
| Settings | `BOT_MAX_LOCAL` (default 1) replaces `MAX_ACTIVE_BOTS`, which is **still read** as an alias so an existing server `.env` keeps working with no edit; the new name wins when both are set. `USER_BOT_LIMIT` (default 2). Both are `>= 0` (0 = no new bots, a drain); a negative value stops the app at start-up. Safe defaults: **no server `.env` change is needed** |
| Neutral busy | The `bot_busy` text is the one it already had ("The note taker is busy right now. Try again in a few minutes."): no name, address, id, title or hint that anyone is recording. A test makes another user's meeting with a title and a code and checks none of it appears in the response |
| `user_limit` words (finding 7) | "You have reached the most bots allowed at once (N). Wait for one to finish first." With the limit at 0: "New bots are not available for your account right now." It never says how many bots are "in meetings", because meetings being written up count toward the limit too |
| Retry of a refused meeting meeting a Vexa duplicate | `send_again(..., raise_duplicate=True)`: the neutral 409 `meeting_has_note_taker` instead of a 502 `bot_send_failed`. The worker's automatic resend still treats it as a plain failure |
| `bot_already_active` | Retired. A user's own running meeting now fills the slot like anyone else's (`bot_busy`) while `BOT_MAX_LOCAL` is 1. With room for more, the own-bot rules are `user_limit` and `already_in_meeting`, which are about the user's own bots and so may say so |

### Sequences tried against the placeholder and the code (self-attack, all in `tests/test_placement.py` unless noted)
| Sequence | Result |
|---|---|
| Uncertain send, **Cancel**, late bot lands, worker polls, Cancel again | first Cancel refused `bot_starting`, row untouched, no stop; the late bot is adopted and pinned; Cancel then works and stops the bot |
| Uncertain send, **End** | refused `not_endable`, no stop |
| Uncertain send, owner **pastes again** | `already_in_meeting`, host never asked |
| Uncertain send, a **second user** pastes the same code | `meeting_has_note_taker`, nothing sent |
| Uncertain send, worker **reaps** at 61 s, owner pastes again | first row `failed`; the new paste gets a fresh bot |
| Uncertain send, **reaped**, the late bot lands anyway (orphan), a second user pastes | the host refuses as a duplicate: `meeting_has_note_taker`, no meeting row, and no stop (the orphan is not touched by a stranger's request) |
| User A **cancels** (row failed, Vexa shows her bot `stopping`), user B pastes the same code and his send gets a 5xx | B's placeholder does not adopt while the bot is `stopping`, nor when it reads `joining` again (its id is A's row's); it is reaped at 61 s |

## Operate / roll back
- **Server steps before merge: none.** `BOT_MAX_LOCAL` and `USER_BOT_LIMIT` are optional. If the server `.env` has `MAX_ACTIVE_BOTS`, it keeps working.
- To stop all new bots without a deploy: set `BOT_MAX_LOCAL=0` and restart `web` and `scheduler` (every request then answers `bot_busy`).
- A bot is "unrecorded" only if the process dies between a send and the commit, or if Vexa takes longer than `UNCONFIRMED_GRACE` (60 s) to start a bot whose answer was lost and the last stop found nothing; Vexa's `automatic_leave` ends it. Everything else (a clear no, a lost answer, a failed save) is settled by the code.
- Roll back: revert the PR. There is no data change; the lock number is not stored anywhere.

## Follow-ups
- **FE guide (queued for C17):** `docs/fe-integration-guide-owner-app.md` still says `bot_already_active` and `MAX_ACTIVE_BOTS` in "One bot at a time per user" (a banner marks it). It must be rewritten with **captured** responses from the running app for `bot_busy`, `user_limit`, `already_in_meeting` and the new **`meeting_has_note_taker`** (409, "A note taker is already in this meeting."): no capture has been taken, so none is pasted. The front end shows `message` as it comes, treats `bot_busy` as "try again later" (no automatic retry loop on a pasted link; a second paste during someone's send is told busy at once), and never expects a name in any of them.
- **Deploy overlap (review finding 5, acknowledged, not changed):** the old code used the single-key lock 6001 and this one uses (6004, 1), so for the moments when the old `web` is still finishing a request while the new one starts, two placements can overlap and go one over `BOT_MAX_LOCAL`. The deploy gate already refuses while a meeting is `bot_sent` or `processing`, which is the protection; nothing else is needed.
- **A plain retry sets `processing` without the placement lock (finding 6, acknowledged, not changed):** `retry_meeting` for a failed transcription flips the meeting to `processing`, which counts toward capacity, with no lock. It cannot send a bot (no capacity is spent on the host), it can only make the count momentarily one higher than a concurrent placement read, which at worst gives that placement a `bot_busy`.
- **Should `processing` count toward capacity at all? (finding 6)** Reviewer and lead view: capacity should count only live bots (`bot_sent`), and the worker should not hold a slot while transcribing. **Not changed here, on purpose:** it is a one-line change in `placement.HOLDS_A_SLOT`, but the worker handles one meeting at a time and holds it through the whole transcription, so with a new live bot beside a long transcription the new bot would sit unseen as "Checking on the bot..." (`docs/sop/2026-11-03-bot-end-controls.md`) and its end would be noticed late. Do it with D9a (worker concurrency), or together with C12, and adapt the existing tests that use `processing` as the busy case. Counting `bot_sent` alone is also what spec 9.4 step 3 says.
- **The worker's automatic `_resend` (`pipeline.py`, review Low):** it sends a fresh bot without the placement lock or the pre-flight, and its uncertain-send placeholder and last stop are not guarded by `may_stop_bot`. That is safe only while there is at most one `bot_sent` row per meeting code (today's pre-flight guarantees it); C12 must revisit it when it takes over sending.
- **`meeting_has_note_taker` tells anyone who pastes a link that some note taker is in that meeting (review Low, accepted):** it names nobody, and the bot shows in the call to every participant anyway.
- **Automated security review of the second round (acknowledged):** (1) adoption by code now pins Vexa's id, as the review asked; that Vexa's by-code `id` is the same id `send_bot` returns is taken from the recorded transcript fixture, not from a live capture. (2) After the grace the meeting is failed and the code gets one last stop; the worker does not poll a failed meeting, so there are no later stops (Vexa's `automatic_leave` is the backstop); the grace itself now counts from the send. (3) The stop after a failed commit re-takes the lock and re-checks the code, as asked.
- **Review leftovers, accepted (second review):**
  - The 3 s lock wait is a `time.sleep` in a sync worker thread: a burst of creates ties up to one thread each for up to 3 s (the connection is not held).
  - "A note taker is being set up for another meeting" also shows for the user's **own** double click, where it is slightly wrong; wording that fits both (for example "A note taker is being set up. Try again in a minute.") is a one-line change if the designer agrees.
  - An uncertain send followed by a flush or commit failure stops once, so a late bot can still have no row, and the worker cannot see it either. A leftover would be found by an admin check of Vexa's running bots against meetings with `bot_sent` (D3 or a small admin script); none exists yet.
  - `send_again` resetting `started_polling_at` on an unconfirmed resend makes `usage.hours_used` count that meeting's live time from the resend, not from its first send: a slight undercount of an estimate that over-counts anyway.
  - Deleting an account (`deletion.purge_user`) while a placeholder exists stops by code (nothing found) and deletes the rows: a late bot would be an orphan. A window of a minute at most.
  - FE: the owner-app guide needs `bot_starting` (409 on Cancel) and `can_cancel: false` with "Starting the bot", with captured responses, in the C17 rewrite.
- **A late bot after the grace:** a Vexa that takes more than 60 s to start a bot whose answer was lost can still leave a bot that has no row (the last stop found nothing). Raise `UNCONFIRMED_GRACE` if the live host shows slow starts; a reconcile against Vexa's running bots (D3) would close it.
- **C12:** lock the join row `FOR UPDATE` **before** calling `place_bot` (never after), re-check the connection and rule state, and decide what a calendar `already_in_meeting`, `meeting_has_note_taker` and `user_limit` mean for a join row (a row for a meeting someone else already has a note taker in should end `skipped` with plain words). `place_bot` commits, so C12's "joined" row update is a second transaction: if that gap matters, add a hook that runs before the commit.
- **D4:** the host id (second lock int) and the per-host capacity count; `PlacementRequest` gains the host. Per-user Vexa keys would lift the one-bot-per-code limit (and make `stop_bot` unambiguous).
- Confirm with a live host what Vexa answers to a second bot for the same code, and what `stop_bot` does when the bot is not ours.
