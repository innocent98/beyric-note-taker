# SOP: edge secret for the client address, and tighter login limits

> **Update 2026-11-03 (PR #28, `chore/remove-trusted-proxy-fallback`):** the transitional address-trust fallback is deleted. `trusted_proxy_ips` and the trust of `next`'s address are gone from `app/config.py` and `app/edge.py`. With `EDGE_SHARED_SECRET` unset the app never believes `X-Forwarded-For`: the client is the socket peer, which behind Docker is the proxy, so every visitor shares one login limit. Rows and sections below that describe the fallback are marked as superseded. A leftover `TRUSTED_PROXY_IPS` in `.env` or the environment is ignored (`Settings` has `extra="ignore"`; a test proves it).

## What shipped
FastAPI now believes `X-Forwarded-For` only on a request that carries a shared secret (`X-Edge-Secret`) that nginx adds; trusting a proxy by IP address is gone. The login limits are 5 failed attempts per 5 minutes per client address plus 10 failed attempts per hour per account, and the owner's browser carries a signed "known device" cookie that skips the account limit so strangers cannot lock the owner out. Branch `fix/login-limits-and-edge-secret`, PR #25, merged 2026-11-03 06:37 UTC and deployed 06:41 UTC. The live `/health` returns `x-edge-ok: true` (checked 2026-11-03 08:25 UTC), so nginx and FastAPI agree on the secret. Adebayo reported the cleanup step (delete `TRUSTED_PROXY_IPS` from the server `.env`) and a first login done; neither was checked from here. Closes the blocker in `docs/spike/nextjs-scaffold/forwarded-for-trust.md`.

## Why
The limiter keyed on `X-Forwarded-For`, which uvicorn applied when the peer was a "trusted proxy" (the Docker bridge gateway `172.28.0.1`, and `next` at `172.28.1.10`). Docker rewrites the source of any connection from another network, or from the host's loopback, to that gateway, so the peer address cannot tell nginx from a hostile container. Any container on the shared server (the worst case is a compromised Vexa container running Chrome on untrusted meeting pages) could send a forged `X-Forwarded-For`, reset its own limit, or burn the owner's attempts. The meetings hold confidential transcripts and open sign-up (10 pilot accounts) comes next, so the gap had to close first. Adebayo chose, on 2026-11-03, "do what's right from the start": an edge secret (option 2 in the spike note).

## How
| Piece | Decision |
|---|---|
| Who adds the secret | **nginx**, on every proxied request, from a root-only file (`/etc/nginx/snippets/beyric-edge-secret.conf`) that `deploy/nginx.conf` includes. `proxy_set_header` replaces any `X-Edge-Secret` or `X-Forwarded-For` a client sent. The value is in no git repo. |
| Next | Passes the headers on unchanged: the fallback rewrite forwards them as received (checked live), and `web/lib/api/server.ts` adds `x-edge-secret` to the headers its server-side calls forward. Next holds **no secret and no check** (compose gives it no env file): validation lives in one place, FastAPI. A request that reaches Next without passing nginx has no valid secret to forward, so FastAPI ignores its address. |
| FastAPI | New `app/edge.py`: `client_address(request, settings)`. With `EDGE_SHARED_SECRET` set: believe the forwarded address only if `X-Edge-Secret` matches (`hmac.compare_digest` on bytes, so a non-ASCII header is a mismatch, not a crash). The forwarded address is the **last** `X-Forwarded-For` entry (the one the trusted edge wrote), must parse as an IP, and is normalised; anything else falls back to the socket peer. |
| uvicorn | Runs with `--no-proxy-headers` (`compose.yaml`) so it never rewrites the peer from `X-Forwarded-For` before the app looks. `--forwarded-allow-ips` is gone. A test reads `compose.yaml` to keep it that way. |
| Rollout safety | `EDGE_SHARED_SECRET` unset: the app starts, logs a **warning** at startup (production only): "EDGE_SHARED_SECRET is not set; every client is limited as the proxy's address". `X-Forwarded-For` is never believed then (since the fallback removal, PR #28; originally the app fell back to believing it from `TRUSTED_PROXY_IPS` peers plus `172.28.1.10`, which was forgeable). A secret shorter than 32 characters also warns. The app never refuses to start. |
| Limiter | `LoginLimiter` has two sliding windows: per client address (5 / 300 s) and per account (10 / 3600 s), checked and counted together under one lock before the password is compared. A refused attempt is not counted, so hammering while locked does not extend the wait, and an address over its limit does not spend the account's budget. Account names are compared lower-cased and trimmed, capped at 254 characters. Unknown accounts are limited exactly like known ones (the key is only the name given). |
| Success | A good login gives back **its own** address attempt and clears that account's failures. It no longer clears all of the address's failures: once accounts exist, a visitor with an account of their own could otherwise log in to it between guesses at someone else's. (The old code reset the address on success.) |
| Known-device cookie | On every **successful** login the app sets a signed cookie: HMAC-SHA256 (key from `session_secret` + `owner_password` with its own label, so it is not a valid session cookie and vice versa), 90 days, `HttpOnly`, `SameSite=Lax`, path `/`, no `Domain`. Named **`__Host-device`** when `COOKIE_SECURE` is true (production: the browser then insists on `Secure`, path `/` and no `Domain`, so a sibling subdomain cannot plant one), plain `device` otherwise so local http tests work. The signed body holds the **account** it was issued for (so with several accounts one user's cookie cannot skip another's window), a random **device id** (`did`, 16 random bytes; a device keeps its id when it logs in again, a new browser gets a new one) and the issue time. A request carrying a valid one for the account being logged in to **skips the account window** (neither refused by it nor counted in it) but is still held to the per-address window (5 per 5 min) **and to a per-device-id window (10 failures per hour)**, so a stolen cookie keeps a cap; over it the request is refused like the account window. A known-device **success gives back its own attempts and does not clear the account's failures** (they belong to whoever was guessing); a success without the cookie, which proved the password, still clears them. Never set on a failed login. A forged, malformed, expired, future-dated or other-account cookie, or one signed before a password or session-secret change, gets no bypass. **Not cleared on logout and deliberately not tied to the session epoch** (a security review suggested revoking it with logout-everywhere; not done): it grants no access (the password is still checked), logout is routine, and clearing it would put the owner back inside the lockout window exactly when they need to log in again. Retired by changing the owner password or the session secret. |
| Lockout log | A refusal by the account or device window logs a warning naming the limit, the account and the client address (no password material, no secret), **at most once a minute** (`edge.Throttle`, shared with the missing-secret warning). Address-window refusals are not logged. |
| Missing secret | With a secret configured, a request from `next`'s own address (`172.28.1.10`) that lacks a valid `X-Edge-Secret` (other than `/health`) logs a warning at most once a minute (the request path is logged with `%r`, so a crafted path cannot forge log lines): nginx lost the include, or something on the server is calling `next` directly. `GET /health` returns the same `ok` body plus a header `X-Edge-Ok: true` when that request carried the right secret and `false` otherwise (also `false` when no secret is configured). The body and status are unchanged, so `deploy.sh` and the container health check are unaffected; `deploy.sh` reaches `/health` without nginx and so reads `false`, which is expected. Public check: `curl -sI https://notes.beyrictech.com/health \| grep -i x-edge-ok`. |
| IPv6 | An IPv6 client counts as its `/64` (one customer owns a whole `/64`; keying on the full address would let them rotate through 2^64 identities); IPv4-mapped IPv6 counts as the IPv4 address. Applied in `edge.limiter_key` to the forwarded address and the peer. nginx's own `limit_req` keys on `$binary_remote_addr`, which is per `/128` for IPv6, so the 6-a-minute edge limit can be dodged by rotating inside a `/64`; the app's limit (per `/64`) still holds, and the nginx key was left alone. |
| Bounded memory | Each limiter window holds at most 50,000 keys; expired keys are dropped as they are touched and by a sweep every 30 s; past the cap the key **created** longest ago is forgotten (a flood of distinct keys can weaken the limit for forgotten ones, never grow memory or refuse anyone). |
| Account for now | The login has only a password, so the account key is the constant `owner` (`services.OWNER_ACCOUNT`). The accounts work passes the email instead (`services.log_in(..., account=email)`). |
| 429 message | Both limits answer with the same body: `{"error": {"code": "too_many_attempts", "message": "Too many failed attempts. Try again later."}}` (was "...Try again in 15 minutes."). The lockouts are now 5 minutes or up to an hour, and saying which would leak which counter tripped. `code` is unchanged; the FE guide says to switch on `code`. |
| Kept | nginx's edge limit on POST `/login` and `/api/session` (6 a minute, burst 3): it sits in front of, and does not conflict with, the app's 5 per 5 minutes. |
| Rejected | Option 1 (`next` on host loopback, `network_mode: host`): closes only the `next` path, cannot be tested on Docker Desktop, and does not help a Vercel deployment later. Next validating the secret itself: puts a secret in a second service for no gain. Refusing to start without the secret: turns a missed deploy step into an outage. |

## Operate / roll back
**Order matters; the exact commands are in `deploy/README.md`, section 6, "Edge secret". The secret is never printed: it lives in a shell variable and is written straight to the two files.**
1. Generate once into `$SECRET` (`openssl rand -hex 32`), write the root-only nginx snippet `/etc/nginx/snippets/beyric-edge-secret.conf` (mode 600, root) holding `proxy_set_header X-Edge-Secret "<value>";` and append `EDGE_SHARED_SECRET=<same value>` to `/opt/beyric-note-taker/.env`, from the same variable; `unset SECRET`.
2. Prove the two files agree without showing either value (`cmp -s` of the two extracted values prints `same` or `DIFFERENT`). Step 1 deletes any existing `EDGE_SHARED_SECRET=` line in `.env` before appending the new one, so a rotation leaves exactly one.
3. Add `include /etc/nginx/snippets/beyric-edge-secret.conf;` to the live site file `/etc/nginx/sites-available/beyric-notes` next to the other `proxy_set_header` lines (edit by hand; the live file has certbot's lines). `sudo nginx -t && sudo systemctl reload nginx`. Until the app has the secret nothing changes for visitors.
4. Deploy (the merge to `main` deploys), or `docker compose up -d --force-recreate web`, outside any `bot_sent` or `processing` meeting.
5. Check: `docker compose logs web | grep EDGE_SHARED_SECRET` prints nothing; `curl -sI https://notes.beyrictech.com/health | grep -i x-edge-ok` shows `true`; the README spoof test still ends in `429`; log in once (that also gives the owner's browser its device cookie). Do this in the browser the owner normally uses.

If the PR deploys **before** steps 1 to 3, nothing breaks: the app logs the warning and (as originally written; **after the fallback removal this is no longer so**) trusted the old addresses. Now, with the secret unset or not matching, every visitor shares one bucket of 5 failures per 5 minutes: no one is wrongly let in, but the owner can be locked out by a stranger's failures until the secret is in place. If steps 1 and 2 are done but 3 is not, the same. If nginx has the include but the file is missing, `nginx -t` fails and nginx keeps the old config: fix the file, do not skip the test. If `.env` has the secret but nginx does not send it, every visitor shares the address of `next` (one bucket of 5 failures per 5 minutes for everyone; no one is wrongly let in): do step 2. **Roll back:** revert the PR and redeploy; the nginx include line can stay (it is only a header the old app ignores) and `EDGE_SHARED_SECRET` in `.env` is ignored by old code. Rotate the secret by repeating steps 1 to 4 with a new value (replace the old `.env` line and snippet).

## Residual risk
- **Account lockout** (security review, fixed in this PR): strangers could keep the owner out of *new* logins with a few failed guesses an hour. Now the owner's browser, holding the signed `device` cookie from a previous login, skips the account window. Still open: (a) a **new** device (or after clearing cookies, or after a password change) has no cookie, so for up to an hour after a stranger's burst of failures the owner can only log in from a browser that already has one; the lockout is logged (`login refused: account ...`) so it can be noticed; (b) a stolen device cookie moves the thief from the account window to a 10-failures-an-hour window of its own, besides the address limit; (c) the cookie cannot be revoked without changing the owner password or session secret. A stolen cookie is now capped at 10 failures an hour on its own device id, besides the address limit.
- Accepted (second review): an owner on a **brand-new browser** can still be locked out for up to an hour after strangers' failures (no cookie yet); anyone **sharing the owner's IPv4 address, or IPv6 `/64`**, shares their 5-per-5-minute address window, so a housemate or office neighbour can lock that address for 5 minutes (the cookie does not help against the address window by design); IPv6 keys are the plain `/64` of the address, so 6to4 and other tunnelled addresses fall under whichever `/64` they map to (one tunnel prefix can look like many users, or the reverse); `GET /health` is public and its `X-Edge-Ok` header reveals whether the secret is configured and matched for *that* request (it cannot be used to learn the secret: a 256-bit value is not guessable one request at a time, and it is `false` for any wrong value).
- ~~Until step 3 of the rollout, and while `TRUSTED_PROXY_IPS` is honoured, the old forgeable trust still applies.~~ Closed by the fallback removal: no address is trusted any more. The cost is that a deploy without a working secret puts every visitor in one limit bucket.
- A process that can read the server `.env` or nginx's root-only file has the secret; at that point it already has the owner password and the database password.
- uvicorn's access log now shows the peer (Next's address), not the visitor; nginx's access log has the real address. The app does not log the resolved address.
- In-memory counters reset on restart and are per process (one `web` process today). With more workers, or a restart loop, the limit weakens; move them to the database or Redis with the accounts work.

## Fallback removal (2026-11-03)
**What shipped:** the app no longer trusts any peer address. `trusted_proxy_ips` (`app/config.py`) and `_legacy_trusted_peers` (`app/edge.py`) are deleted; `client_address` is `forwarded address if the secret matches, else the socket peer`. `NEXT_ADDRESS` stays, but only so `note_missing_secret` can recognise requests that came through `next`; it is not trusted for anything. The startup warning now has one unset-secret branch with the text "EDGE_SHARED_SECRET is not set; every client is limited as the proxy's address". `X-Edge-Ok`, the missing-secret warning and the short-secret warning are unchanged. The app still starts without the secret.

**Why:** the secret went live (`/health` returned `x-edge-ok: true`) and Adebayo deleted `TRUSTED_PROXY_IPS` from the server `.env`, so the fallback was dead weight, and a path that Docker's NAT lets any container forge.

**Stale settings:** `Settings` uses `extra="ignore"`, so a leftover `TRUSTED_PROXY_IPS` in the environment or in a `.env` file is read past without an error and has no effect (`tests/test_edge.py::test_a_stale_trusted_proxy_ips_setting_is_ignored` covers both sources and that the app still starts).

**Files:** `app/edge.py`, `app/config.py`, `tests/test_edge.py` (the two "unset secret keeps trusting" tests became "never believes the forwarded address" tests; startup-warning wording, a stale-setting test and a through-`/login` test from the gateway peer were added; fixtures no longer pass `trusted_proxy_ips`), `.env.example`, `deploy/README.md` (the `TRUSTED_PROXY_IPS` row and the "falls back" wording), `docs/spike/edge-secret/e2e.sh` and `compose.e2e.yaml` (scenario B), dated notes on the older SOPs that named the rule, the checklist.

**Verification:** see the PR description for the full suite, ruff and `deploy/nginx-limit-check.sh` results. The nginx side did not change.

**Operate / roll back:** nothing to do on the server (`TRUSTED_PROXY_IPS` is already gone; if it is still in `.env` it is ignored). A plain `git revert` of the PR restores the old code and needs no server step either: the old code reads `TRUSTED_PROXY_IPS` with its default `172.28.0.1` when the variable is absent. The one thing to watch after this deploys is `curl -sI https://notes.beyrictech.com/health | grep -i x-edge-ok` staying `true`: if it ever reads `false`, all visitors share one login limit until nginx and `.env` agree on the secret again.

**Follow-ups:** re-run `docs/spike/edge-secret/e2e.sh` (needs Docker, builds two images) and refresh `e2e-output.txt` with the new section B.
