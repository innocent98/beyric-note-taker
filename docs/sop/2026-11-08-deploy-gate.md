# SOP: the deploy gate, no deploy while a calendar join is due (2026-11-08, plan task C16, spec Q19)

**What shipped:** `deploy/deploy.sh` now refuses to deploy while a calendar join is due within 10 minutes, with one line naming the earliest due time, unless `ALLOW_DEPLOY_WITH_JOINS_DUE=1` is set for that deploy. New: `deploy/gate.sh` (`join_due_soon`, `deploy_gate`), `deploy/deploy-gate-check.sh`. PR: see the PR for branch `feature/c16-deploy-gate`.

**Why:** auto-join is live. It starts a bot with nobody pressing anything, so a deploy that restarts `web`, `worker` and `scheduler` just before a join is dispatched can drop that recording. Merge to `main` deploys by itself, so nothing else stood in the way.

**Premise corrected:** the plan and spec describe the gate as an addition to a refusal "while a meeting is `bot_sent` or `processing`". `deploy.sh` has no such refusal and never had: that rule is advice in `deploy/README.md` only. This change does not add one (out of scope; a meeting in `bot_sent` or `processing` still does not stop a deploy).

**How:**

| Piece | Behaviour |
|---|---|
| Query (`gate_sql`) | `min(run_at)` over `scheduled_joins` where `state in ('scheduled','no_capacity','dispatching')`, `run_at <= now() + 10 minutes` and `deadline_at >= now()`. A join past its `run_at` but inside its deadline still counts (the runner may be about to send it); one past its deadline never does, so a stuck old row cannot block deploys forever |
| `join_due_soon` | exit 0 nothing due; exit 1 due (earliest `run_at` in UTC on stdout); exit 2 the database could not be asked or answered with something that is not a time |
| `deploy_gate` | what `deploy.sh` calls. 0: go ahead. 1: refuse with one line. Exit 2 also refuses (fail closed) with its own line |
| Override | the exact value `ALLOW_DEPLOY_WITH_JOINS_DUE=1` in the environment turns a refusal, due join or unreachable database alike, into a one-line `WARNING` and a deploy. Any other value (`0`, `yes`, empty) refuses |
| Where it runs | in `deploy.sh` right after the "is the SHA on origin/main" check and before the backup, so a refusal changes nothing |

Decisions: the SQL goes through `gate_psql`, a one-line function (`docker compose exec -T db ... psql`, the same way `scheduler_beat_since` already asks) that the check script replaces with a psql to a scratch database, so the real query and decision code run unchanged. `gate.sh` is read by `deploy.sh` at the top of the file, before `main` runs, like the rest of the script it cannot change mid-run. The override is an environment variable because the CD key's forced command takes only the SHA. The unreachable-database case is also overridable on purpose: otherwise a broken database would block the very deploy that fixes it. Rejected: waiting for the join instead of refusing (the CD job has a 20-minute limit and holds the deploy lock), a flag argument (cannot pass the forced command), adding the `bot_sent`/`processing` refusal here (a separate decision).

**What's involved:** `deploy/gate.sh` (new), `deploy/deploy.sh` (a `source` line at the top and `deploy_gate || return 1`), `deploy/deploy-gate-check.sh` (new), `deploy/README.md` (section 8, "Deploying while a join is due"), `tests/test_deploy_script.py` (copies `gate.sh` into the fixture project; the docker stand-in answers the gate's query; 7 new tests, 11 cases). No Python in `app/`, no migration, no config. Table and columns read from `alembic/versions/0010_calendar.py` and `app/models.py:589` (`ScheduledJoin`): `scheduled_joins.state`, `run_at`, `deadline_at` (the last two `timestamptz NOT NULL`), and the check script builds the schema with the real migrations.

**Verification:** `deploy/deploy-gate-check.sh` against Postgres 17 (container `nt-pg-54351`), schema built by `alembic upgrade head`: 35 checks pass (joins at -1 h, +5 min, +20 min; the +9/+11 minute edges; an overdue join inside its deadline; each state; several joins name the earliest; the override with `1` and with `0`, `yes`, `true`, empty; unreachable database; a database without the table; an odd answer). `tests/test_deploy_script.py`: 25 pass. `shellcheck -x` clean on the three scripts. A dry run of the real `deploy.sh` with stand-in `docker`, `git` and `curl` against that database refused with a join due in 5 minutes (zero docker or git calls made), deployed with the override and with the join gone, and refused with the database unreachable; output in the PR body. Not run on the live server or a full compose stack.

**Operate / roll back:** the refusal fails the CD run with the line in its log. Wait for the join to start, then re-run the failed `deploy` workflow, or deploy by hand with the override for an emergency (`ALLOW_DEPLOY_WITH_JOINS_DUE=1 deploy/deploy.sh <sha>`; commands and the temporary `authorized_keys` route are in `deploy/README.md`). Never leave the variable set. **The deploy that ships this change is not gated** (the script already on the server is the old one); the gate applies from the next deploy. To remove the gate: delete the `source` line and `deploy_gate || return 1` in `deploy.sh` (or revert the PR); `gate.sh` and the check script can stay.

**Follow-ups:** (1) a `bot_sent`/`processing` refusal does not exist in `deploy.sh` despite the plan's wording: decide whether to add one using the same shape. (2) The check script is not in CI (CI runs no deploy check scripts, and this one needs Postgres plus the Python environment for migrations); run it by hand after touching `gate.sh`. (3) The window is a fixed 10 minutes; make it a setting only if it proves wrong.
