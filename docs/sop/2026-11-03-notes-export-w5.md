# SOP: download the notes as PDF or Word (AI workspace phase W5)

## What shipped
The meeting page has a **Download** menu (PDF, Word, "Include the full transcript") and the API has `GET /api/meetings/{id}/export?format=pdf|docx&transcript=true|false`, which builds the file when asked and never stores it. Branch `feature/notes-export-w5`, PR [#48](https://github.com/innocent98/beyric-note-taker/pull/48) to `main`. No table, no column, no setting, no migration. Spike EX1 (WeasyPrint against the image and memory) came first: `docs/spike/export-pdf-memory.md`, verdict "fits".

## Why
The designer's prototype has a Download menu that the app lacked, and the AI workspace spec (section 9, decision D9) made it pilot work: the notes are the product and people want them in a document. W5 is independent of the other phases: it renders the notes as stored, with no extraction, no team and no translation.

## How
| Piece | Decision |
|---|---|
| One render model | `NotesDocument` (`app/notes_document.py`): title, a meta line (date, platform, duration), ordered sections of blocks (paragraph, heading, list with nesting, quote, code), optional transcript turns, footer. Built from the stored Markdown with the same `markdown-it` settings as the page (CommonMark, no raw HTML, no images). It holds plain text runs, never HTML, so each renderer escapes for its own format. Later phases (email, translation) render from it too |
| PDF | WeasyPrint from an escaped HTML page built from the model, a print stylesheet in the brand colours and the app's Geist font files (`app/static/fonts`), A4, footer "Generated by Beyric Note Taker, 3 Nov 2026" and "page / pages". The transcript starts on a new page. Rejected (spec): headless Chromium, ReportLab |
| Word | python-docx: Title, Heading 1 per section, real bullet and number styles with two nested levels, a transcript after a page break, the footer in the page footer. Rejected (spec): HTML-to-Word converters, pandoc |
| Where it runs | **a child process** per export (`app/export_render.py`, started by `app/export.py` with `python -m`, `cwd=/srv`). A hung render is killed at the limit; the memory a big document needed is returned to the system; the child gets only `PATH` and the library path, never the web process's secrets. One at a time per web process (a semaphore taken without waiting: a second request is 503 `export_busy`, `Retry-After: 5`) |
| Limits | **45 s** time limit (the spec said 60; nginx's `proxy_read_timeout` is 60 s, so 60 would reach the visitor as nginx's error page). `RLIMIT_AS` 2 GiB in the child on Linux. Each export logs seconds, bytes and the renderer's peak MiB (never content) |
| Scoping | the existing `services.meeting_or_404`: another account's meeting is a 404. A meeting that is not `ready` (or has no notes) is 409 `not_ready`. No rate limit beyond the semaphore (the spec's "per account" limit for export has no number in section 10; see follow-ups) |
| File name | the meeting's title with `/ \ : * ? " < > |`, control characters and line breaks removed, spaces collapsed, 100 characters at most, "meeting-notes" if nothing is left; `Content-Disposition: attachment; filename="<ascii>"; filename*=UTF-8''<percent-encoded>`, plus `Cache-Control: no-store` and `nosniff` |
| Not stored | nothing is written to the database or disk by the app; the bytes exist in the response. The privacy policy says so (Information we collect, Meeting content: "files you export are built when you ask and are not stored"), in the Jinja page and the Next copy |
| The menu | `web/components/app/download-menu.tsx`. A `details` menu (the existing `Menu` pattern, closed on outside click and Escape by `behaviors.tsx`), the designer's two tiles, the transcript tick shown only when the meeting has a transcript. The file is fetched with the session cookie, handed to the browser as an object URL with `<a download>`, so errors can be shown instead of navigating to JSON. States: **preparing** (button and a line), **done** ("<name> downloaded" for 8 s), **failed** (the server's message), **not ready** (disabled button with its reason; a failed meeting shows no button; a 409 refetches the meeting) |
| Left out on purpose | the prototype's language note under the tick and a translated download (W7), Share (W6). The prototype's toast is a line under the header (no toast component exists yet; Stream D16) |

## Verification
- Unit and API tests: see above; `ruff check`, `ruff format --check`, the new and touched test files, `npm run lint`, `typecheck`, `vitest run` (all) were run locally. CI is the full suite.
- **Live:** the real app inside the real image (`docker build .`), a scratch Postgres, real HTTP, `--memory=512m`: every success and every error in the FE guide was captured; the 503 by a genuine second request during a long render. 504 and 500 were provoked inside the capturing process (a 0.2 s limit; an unloadable PDF library) and are labelled so.
- **Looked at:** the PDF rendered to images (Geist, bold weights, nested bullets, accents and Yoruba letters, footer and page numbers, the transcript on its own page) and the Word file through python-docx and macOS's reader. **Not opened in Microsoft Word, Google Docs or Pages**; macOS's reader flattens nested bullets and ignores the page break, so those two details of the Word file are unchecked in a real Word.
- **Browser:** the menu, the preparing and downloaded lines, the disabled state and a phone-width menu in the embedded browser against `next dev` proxying the real app. That the browser wrote the file to disk was not observable there. Safari, Firefox and the production CSP were not tried.
- **EX1 numbers** (arm64 Docker VM, loaded machine, `docs/spike/export-pdf-memory.md`): 1 hour of speech, PDF with transcript 1.9 s and 91 MiB renderer peak; 3 hours 5.0 s and 103 MiB; 40,000 words 9.0 s and 120 MiB; Word 45 to 47 MiB, 0.5 to 1.5 s.

## Operate / roll back
- Deploy: the image rebuild installs the two new Python packages; no environment variable, no migration. Check after deploy: open a ready meeting, Download, PDF with the transcript ticked; the `web` log gets one line `export: pdf built in ... renderer peak ... MiB`.
- If exports fail after a deploy, `export_failed` is logged as `the pdf render exited with status N` with no content; run `docker compose exec web python -c "import weasyprint"`: an `OSError` naming a library means Pango is missing from the image.
- **`web` now has `mem_limit: 768m`** in `compose.yaml` (it had none; `next` has 512m, `vexa` 3g). Measured: the app is about 90 MiB idle and one export adds about 100 to 120 MiB (child process), so about 210 MiB at worst; 768m leaves room for the rest of the app. The export also has its own child limit (2 GiB address space).
- Roll back by reverting the PR: no data was written, so nothing is left behind. Users lose the Download button and nothing else.

## Server steps before merge
- **Free disk first** (`df -h`, `docker system df`): the first deploy rebuilds the `web`, `worker` and `migrate` image (they share one build) with the two Pango packages named in the Dockerfile and one pip layer of about 103 MB (WeasyPrint, python-docx and dependencies); the finished image was 264 MB in total on arm64. On the shared server, prune old images if free space is tight.
- No new environment variable, no migration, no nginx change. `compose.yaml` changes: `mem_limit: 768m` on `web` (the container is recreated on deploy).
- After deploy: open a ready meeting, Download, PDF with the transcript ticked; the `web` log gets `export: pdf built in ... renderer peak ... MiB`.

## Follow-ups
- The prototype's language note and translated downloads wait for W7 (`NotesDocument` already takes the text it renders; the translated sections come from the same parser). Share (W6) reuses the same document and the PDF and Word renderers for its attachments.
- A per-account export rate limit (the spec's section 3.3 mentions one; section 10 gives it no number). Today the semaphore bounds the cost; add a limit if the pilot shows abuse.
- Per-turn transcript timestamps (spec follow-up) are not stored, so the exported transcript has none.
- Link addresses in notes are printed after their text, not clickable, in both formats.
- Open one export in real Word and Google Docs and update this SOP (nested bullets and the page break before the transcript are the two details to look at).
- A toast component (Stream D16) would replace the status line under the header.
