# SOP: JSON API for the Next.js frontend (stream B)

## What shipped
A JSON API under `/api/` that does everything the Jinja owner pages do: session (login, logout, CSRF token), meetings (list, detail, create, cancel, retry, regenerate), templates (list, create, update) and vocabulary (list, create, delete). Branch `feature/json-api`; PR in the final report. The Jinja pages are unchanged and keep working.

Frontend contract: `docs/fe-integration-guide-owner-app.md` (every payload captured from the running app, in `docs/fe-captures/owner-app/`). Schema for type generation: `docs/openapi.json`.

## Why
Decision of 2026-11-02 (`docs/superpowers/specs/2026-11-02-nextjs-migration-plan.md`): the frontend moves to Next.js, which calls FastAPI over JSON. FastAPI stays the system of record for auth, data, the worker, Vexa and OpenAI.

## How
- **Rules live in one place.** The work the Jinja handlers did inline moved to `app/services.py`: login and logout, create, cancel, retry and regenerate meeting, save template, add and delete term, the status text, tone and `retry_block`, the markdown renderer, the id convertor. Each action either succeeds or raises `Refused(status, code, message)`. `app/web.py` catches it and renders the page with the same message as before; `app/api.py` lets it propagate to one handler that returns JSON. The messages and statuses are therefore identical on both sides, and every one of the 338 existing tests passes unchanged.
- **Auth path kept small** (`app/auth.py` `guard`, the part to review):
  - The guard reads the path from the ASGI scope (`auth.request_path`), not `request.url`, which is also built from the client's `Host` header; `starlette>=1.10` is required as well. A test sends odd `Host` headers.
  - `/api/*` needs a login except `GET` and `POST /api/session` (`PUBLIC_API`, an exact method-and-path set).
  - Every method except GET, HEAD and OPTIONS under `/api/` needs the header `X-CSRF-Token`, compared with `hmac.compare_digest` against the session's token (`_csrf_matches`, also used by the form path now). No body is read for it.
  - Page paths behave exactly as before (login redirect, `csrf_token` form field on POST).
  - Login (`POST /api/session`) is public but still needs the CSRF header; the limiter is the page's (`LoginLimiter`, same instance, same 5 in 15 minutes).
- **Errors** (`app/api.py` `install_errors`, plus the 401 and 403 handlers in `app/main.py` beside the page versions): on `/api/` paths every error is `{"error": {"code", "message"}}`: 401, 403, 404, 405, 422 (adds `fields`, never the submitted values), 500. Other paths keep their old handling; the 500 handler returns the same plain text Starlette's default does.
- **Bodies are strict** (`app/api_schemas.py`): pydantic `strict` and `extra="forbid"`, so `"template_id": "1"` or an unknown field is a 422. Business rules (URL, name length, duplicates) stay in the services and answer 400, like the pages.
- **Notes**: raw markdown (`notes`, for copying) plus `notes_html` from the existing `render_markdown`. The guide tells the frontend to show `notes_html`.
- **OpenAPI**: `scripts/export_openapi.py` builds the schema from the API router (the running app keeps `/openapi.json` and the docs off) and writes `docs/openapi.json`. Operation ids are the function names.
- **Decisions and trade-offs**
  - The meeting link is never returned (a Zoom link carries its password).
  - `DELETE /api/vocabulary/{id}` on an unknown id is 404; the page redirects either way. A JSON client benefits from knowing.
  - A duplicate template name or term is 400 (as on the pages), not 409, so the shared service gives one status.
  - `GET /api/meetings` has `limit` (default 50, max 100) and `before_id` paging; the page only ever showed 50.
  - Rejected: a separate API service layer (duplicated rules), response models built straight from the ORM (would leak `url`), versioned `/api/v1` (one consumer, same deploy).
  - Known quirk, documented not hidden: FastAPI decodes a JSON body before it runs dependencies, so a logged-out request with a *malformed* JSON body gets 422 rather than 401. Nothing is read, changed or echoed.

## What's involved
| Path | Change |
|---|---|
| `app/services.py` | new: shared actions, `Refused`, constants and helpers moved from `web.py` |
| `app/api.py`, `app/api_schemas.py` | new: routes, response and request models, error handlers |
| `app/auth.py` | `guard`: `/api/` rules, `_csrf_matches`, `PUBLIC_API`, `CSRF_HEADER` |
| `app/main.py` | JSON branches in the 401 and 403 handlers; mounts the API router |
| `app/web.py` | thinner: calls the services (templates, routes and messages unchanged) |
| `scripts/export_openapi.py`, `docs/openapi.json` | schema export |
| `scripts/capture_owner_api.py`, `docs/fe-captures/owner-app/` | live capture harness and its 81 outputs |
| `tests/test_api.py` | 106 tests; `pyproject.toml` ignores F811 for that file (it reuses `test_web.py`'s fixtures) |
| `docs/fe-integration-guide-owner-app.md` | the frontend contract |

No migration, no new dependency, no new setting.

## Verification
- `tests/test_api.py`: session and CSRF, the login limit (shared with `/login`), logout revocation, one cookie for pages and API, every `/api` route enumerated from the app's own schema (401 when logged out except the two session calls; 403 on every write without the header), every meeting state and action, templates, vocabulary, error shapes, no leakage of links or internal error text, OpenAPI outline matches the routes.
- Whole suite run once at the end because auth and shared code changed (result in the PR).
- Live: `scripts/capture_owner_api.py` runs the real migrations on a scratch Postgres, starts the real app under uvicorn with only Vexa and OpenAI faked, and records every exchange over HTTP. **Not exercised**: real Vexa, real OpenAI, the real worker (states past `bot_sent` are inserted by SQL), HTTPS and the `Secure` cookie flag, nginx and Cloudflare, the Next proxy.

## Operate / roll back
Nothing to run or configure. `/api/*` is served by the existing `web` service. Roll back by reverting the PR: the Jinja pages do not depend on the API. To refresh the artefacts after an API change: `python scripts/export_openapi.py` and `python scripts/capture_owner_api.py <postgres url>`, then regenerate the guide's payloads from the captures.

## Follow-ups
- **nginx** (done in this PR after review): `location = /api/session` carries the same POST-only `notes_login` limit as `/login`, and the 300-second `regenerate` location now matches `/api/meetings/<id>/regenerate` too. Not yet checked with `nginx -t` or live. The Next proxy's own timeout for a slow rewrite still needs checking.
- **Login limit behind Next**: if the Next server proxies `/api`, the login limiter sees Next's address unless Next forwards the real client IP and FastAPI trusts it (`TRUSTED_PROXY_IPS`, `X-Forwarded-For`); otherwise all visitors share one bucket. Stream A is handling it.
- **`RETRY_BLOCK_TEXT`** in `app/services.py` repeats three sentences that are also inline in `meeting.html`; a test keeps them equal. They go when the Jinja page is retired.
- TypeScript type generation from `docs/openapi.json` was not run here.
- Later streams will add endpoints (accounts, calendar, share): extend `docs/openapi.json` and the guide with each.
