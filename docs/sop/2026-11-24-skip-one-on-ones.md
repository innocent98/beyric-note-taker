# SOP: "Skip one-on-one meetings"

**What shipped.** A per-person checkbox in Settings, Calendar, under "Also join invites I haven't answered yet": **"Skip one-on-one meetings"** (`user_settings.skip_one_on_ones`, migration `0056`, **off by default for everyone**). When it is ticked, `will_join` does not send the note taker to an event with **exactly two people invited**, under the rules "All meetings with a video link" and "Only meetings I organise". The Upcoming row shows the reason as a visible muted line (the same line `not_accepted` uses). Branch `feature/skip-one-on-ones`; PR: see the checklist entry. Alembic head: **0056**.

## Why

Anthropic's Claude Meetings lets a person auto-join all meetings or all except one-on-ones. Beyric's rule was only all / organiser / none plus the unanswered-invites box, so a person who wanted every team meeting recorded but not their private 1:1s had to switch each 1:1 off by hand, every week. Adebayo chose to close the gap.

## How, and what was decided

| Decision | Choice | Why (and what was rejected) |
|---|---|---|
| What "one-on-one" means | `attendee_count == 2` exactly (`ONE_ON_ONE_COUNT` in `app/gcal_rules.py`) | **The count is people INVITED, not people who attend.** Both providers store it with the owner in it: Google's `attendees` list has everyone (`app/gcal_events.py:168`); Graph's list leaves the organiser out, and `_attendee_count` adds one (`app/graph_events.py:154`), so two means the same. **0** is an event with no invite list (a solo event) and **1** is a list of only the person: neither is a one-on-one and neither is skipped. **Known limits:** a room resource, a group address or a co-host counts as an invitee (a 1:1 plus a room has 3 and is joined); an invite where someone declined still counts them; Google can omit a very large guest list, which only makes the count smaller for meetings that are not 1:1s in practice. **Rejected:** counting only accepted attendees (we store no per-attendee responses, by design). |
| Where the choice lives | A boolean on `user_settings`, `NOT NULL`, **server default FALSE**; new `JoinSettings.skip_one_on_ones` (default `False`) | Nothing changes for anyone until they tick it; existing callers and tests keep working. The model followed was #253 (`join_unanswered`, migration 0055). |
| Where it sits in `will_join` | After the rule (`none`, then `organizer`), **before** the unanswered-invite check, below the person's own switch | The event-forbids checks (declined, no link, cancelled, all-day, too long, over, Teams) come first and are untouched. The per-meeting **override still wins both ways, exactly as for every other rule**: `override=True` joins a two-person meeting, `override=False` never joins a bigger one. Under `organizer` a meeting the person does not organise says `not_organizer` first (the more basic reason). **Before the unanswered check on purpose:** a two-person unanswered invite from a stranger says `one_on_one`, not `not_accepted`, because "Settings can join these too" must not point at a box that cannot help while the skip is on. |
| Reason code | `one_on_one` (in `REASONS`); label **Off** (it is in `OFF_REASONS`: the person could change it); text "Skipped because only two people are invited. Settings can join these too." | Same kind of visible muted line as `not_accepted` (the row already prints `reason_text` for any switch that is not "Will join"; **no change to `calendar-upcoming.tsx` was needed**). The text says "invited", true to the count. |
| Building the settings in one place | `JoinSettings.for_user` reads the new column; **no other constructor exists** | Proof: `grep -rnE "JoinSettings\(" app` finds nothing (the one build is `cls(...)` inside `for_user`), and `grep -rn "JoinSettings.for_user" app` lists every caller below. The callers, all through `for_user`: `calendar_api._join_settings` (the API, Upcoming, override), `gcal_sync.apply_batch` and `rerun_rules` (sync and re-run), `join_runner._gate` (the send-time re-check), `organizer_bot._can_place` (the organiser-bot path), `mail_summary.auto_join_sentence` (the "will join automatically" line in mail). `DEFAULT_USER_SETTINGS` (the stand-in for a person with no settings row) carries `skip_one_on_ones=False`. The `ParsedEventLike` protocol now lists `attendee_count`. |
| API | Extended the existing route: `PUT /api/calendar/settings` takes `skip_one_on_ones` (strict bool, never null); `GET /api/calendar` and the PUT answer carry it. **No new route.** | Route-inventory tests are unchanged. An absent field keeps the stored value; an unknown field is still 422. The validator message names all four fields. |
| Re-running stored rows | A changed `skip_one_on_ones` re-runs `gcal_sync.rerun_rules` over the connection's events exactly as a `join_unanswered` change does: joins it now forbids are **cancelled** with the reason `one_on_one`, joins it now allows are **made or revived**, a join whose bot is in is never touched, and **per-meeting switches are kept** (a rule change clears them; this does not). | Same reasoning as #253. Unlike the unanswered box, clearing the skip needs no "has not started" restriction beyond the 15-minute window every meeting has: the box only ever narrowed a rule the person chose, it does not open the door to strangers. |
| The "Not recorded" and Send now lists | **A skipped one-on-one is a `cancelled` join (the person's own choice), never on "Not recorded", with no Send now.** | Consistent with `override_off`, `not_accepted`, `not_organizer`, `rule_none`: those are all cancelled joins and none is in `NOT_RECORDED_SKIP_REASONS`. "Not recorded" is for meetings the note taker failed to get into, and this one was never meant to be entered. To record one anyway the person flips its switch on the Upcoming list (an override beats the box). |
| Wording kept true | `calendar_text.rule_text(rule, join_unanswered, skip_one_on_ones)` names every exception in force: `all` + skip: "Joining all meetings except unanswered invites from outside your organisation and meetings with only two people invited" (or "... except meetings with only two people invited" when the unanswered box is ticked); `organizer` + skip: "Joining meetings you organise, except meetings with only two people invited"; `none`: "Auto-join is off". The card's rule sentences are built the same way in `settings-calendar.tsx` (`ruleDescription`). | The old labels would be untrue with the box on. In the UI the words are "meetings with only two people invited", never "one-on-one with someone who accepted". |

**LEAD-DESIGNED pieces (not in the designer's file), to be shown to the designer:** the checkbox and its label "Skip one-on-one meetings", its help text ("Off: meetings with only two people invited are joined like any other.", "On: the note taker skips meetings with only two people invited. You can still switch one on from the Upcoming list.", and "Only used with All meetings with a video link or Only meetings I organise." under "Only when I turn it on"), the changed rule sentences and `rule_text` above, and the new Upcoming reason text. They reuse the designer's `Checkbox`, `cal-rules`, `cal-rule-desc` and `meta-line`; **no new style or component**. Under "Only when I turn it on" the checkbox is disabled (still showing the stored value), as the unanswered box is under the other rules.

## Operate / roll back

- Deploy: normal (`alembic upgrade head` adds the column; the code reads it). **Server step before merge: none** beyond the migration the deploy already runs.
- Turn it off for one person: `UPDATE user_settings SET skip_one_on_ones = false WHERE user_id = <id>;` the next sync or send-time check joins their two-person meetings again (planned joins that were cancelled are revived by the next sync or by any settings write that re-runs the rules).
- Roll back: `alembic downgrade 0055` drops the column; people who ticked lose the choice and their one-on-ones are joined again by the rule they chose. Code from before the column ignores it.
