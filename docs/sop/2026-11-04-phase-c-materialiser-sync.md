# SOP: Calendar materialiser and sync job (C8, C8b)

## What shipped
Tasks **C8** (`apply_batch`: calendar events to `calendar_events` and `scheduled_joins` rows) and **C8b** (`sync_connection`, the loop job that runs it for every due connection, and its registration on the scheduler's sync loop) of `docs/superpowers/plans/2026-11-03-pilot-accounts-calendar.md`. Branch `feature/c8-calendar-materialiser-sync`, one PR (number in the PR list). One small additive migration, `0012`. **Nothing runs for users:** the job is registered only while `CALENDAR_ENABLED` is true (false in production until C4 merges), and no bot is sent anywhere: a scheduled join is only a row until the runner (C12) and `place_bot()` (C11) exist.

## Why
The calendar client (C5) and the rules (C6, C7) produce facts; nothing yet turned them into the rows the runner will read. This is the part where a wrong decision loses a meeting (a half-read calendar cancelling joins, a move applied after the bot was sent) or leaks (another user's rows, an attendee list stored), so it is built tests-first and the failure modes are pinned by tests.

## How
| Decision | Why |
|---|---|
| `apply_batch(session, conn, batch, user_settings, *, now, settings=None, vexa=None) -> ApplyResult` commits once at the end; `ApplyResult(created, moved, cancelled, revived, unreadable)` counts **join rows** (plan had the first four) | One transaction per batch means a crash applies all or nothing. The `settings` and `vexa` keywords are injection points for tests; both default to the real ones |
| **Idempotent.** Applying a batch again changes nothing (checked on every column of every row), including a replayed move, cancel, switch-off and sweep | A crash between "batch committed" and "token written" replays the same changes. Only values that differ are written, and `synced_at` is the batch's `now` |
| **Per-user by construction.** Every row written carries `conn.user_id`; every lookup filters on the connection and that user; `ParsedEvent` has no field for another user. The calendar template is used only if the template's `owner_user_id` is the user's (a foreign id gives `template_id = null`) | A malicious event cannot name another user; a tampered setting cannot attach another user's template |
| **Nothing is stored beyond the plan:** `parse_event` already drops description, location and attendee addresses (kept: attendee count, the user's own response, one flag for "organiser is in my Workspace domain"). The Zoom passcode stays only in `meeting_url`, which is never logged | Spec 7.4, 12 |
| **Stranger's invite:** the join decision is C7's `will_join` over the stored row and the user's `override`. Under rule `all` an unanswered invite from outside the user's organisation gets no join row until the user switches it on | A stranger cannot take the only bot slot by sending an invite |
| **Incomplete batch** (a page failed): events are created and updated, **nothing is cancelled**: not an event missing from the list, and not a cancellation stub that arrived with it (the token does not move, so the stub comes again). A decline that arrives still cancels that event's join (it is fresh information about that event, not absence) | Review Focus 1: half a calendar proves nothing about the rest |
| **Complete full batch** cancels events missing from it (row `cancelled`, join `cancelled` with reason `removed`), but only rows that overlap the listed window (`ends_at > now - 1 h`, `starts_at < now + 14 d`) and only joins with no bot sent. An event the batch names but cannot read is not "missing" | An event that ended long ago, or starts after the window, is simply not in a full listing |
| **Join states.** `scheduled` and `no_capacity`: times follow the event (a `no_capacity` row moved to later waits again as `scheduled`; its link is left alone because it holds its meeting code). `dispatching`, `joined`, `completed`, `failed`: moves are ignored, the meeting is the truth (spec 7.8). Cancel (event cancelled, declined, switched off, rule change, link removed): `scheduled`, `dispatching`, `no_capacity`, `skipped` become `cancelled` with the reason (`cancelled`, `removed`, or C7's `declined`, `override_off`, `rule_none`, `not_organizer`, ...). `ended` rewrites nothing | The runner (C12) re-reads the state before it sends, so cancelling a `dispatching` row stops the send |
| **Stopping a bot** only for an explicit calendar cancellation of a `joined` join whose meeting is `bot_sent`: `services.cancel_meeting` after the batch commits. If the pipeline already took the meeting, or Vexa will not stop the bot, the join stays `joined`, nothing is raised, and the calendar change itself is kept. Never done for a missing event or a switch-off | `cancel_meeting` commits and calls Vexa; ending a live recording because an event left a 14-day window would be wrong |
| **Revive** (`cancelled` back to `scheduled`, same row id, attempts and re-check mark cleared) and **create** only while `now <= starts_at + 15 min`. An event already past its deadline and still on gets no row | Spec 7.8 "In progress" with Send now. Otherwise the runner would write a "Not recorded" failure for a meeting nobody tried to join |
| An event started but inside its deadline gets a `run_at` in the past, so the runner dispatches it at once | Spec 7.8 late join |
| Hostile input cannot break a batch: NUL characters are stripped from titles, titles are cut at 1,000 characters, an event whose id or link has a NUL or is longer than the columns is counted as `unreadable` and skipped, any parse exception skips that event (type logged, no text) | One poison event must not stall a user's calendar |
| **`sync_connection`**: full when there is no token, no `last_full_sync_at`, or the last full was 6 h ago or more; otherwise incremental; `SyncTokenExpired` is answered with a full listing in the same run. After `apply_batch` committed a **complete** batch it writes the token, `last_sync_at`, `last_full_sync_at` (only for a full listing) and clears the error. An incomplete batch writes none of them and records an error. Any failure (source, apply, anything) rolls back and is recorded in `last_error`/`last_error_at` as `ExcType: message` for source errors (their messages carry a status or type only) and the type alone otherwise; it never raises | The token write is a second transaction after the batch commit, so a crash leaves the old token and replays harmlessly |
| `AuthRevoked` and 30 minutes of failures are **only recorded** here (`last_error`); C13 turns them into `needs_reconnect` / `degraded` and the notifications | Plan: "until C13 lands, they are recorded in `last_error`" |
| **The job** `sync_due_connections` takes provider-`google` connections in `connected` or `degraded` status of `active` users, whose last sync and last failure are both at least 5 minutes ago (null `last_sync_at` = first sync), oldest id first, at most 50 per run, each in its own commit; one that fails outright does not stop the rest. Registered as `calendar_sync` on the **sync** loop (every 60 s) by `register_calendar_sync`, called from `scheduler.register_jobs` **only if `calendar_enabled`**; the module is not imported otherwise | A failing connection is retried at the same 5-minute pace, not every minute. Suspended users are not synced |
| Migration `0012`: nullable `calendar_connections.last_full_sync_at` | The plan names it and the 6-hour rule needs it; nullable so an existing connection simply starts with a full sync |
| One optional setting, `AUTOJOIN_LEAD_SECONDS` (default 60) | Plan C8; `run_at = starts_at - lead` |

Rejected: writing the token in the same transaction as the batch (it would hide a failure between the two and gain nothing, replay is idempotent); cancelling joins for events outside the window (they are history); stopping bots on absence; one big "reconcile" that also re-runs `will_join` over all stored rows on a rule change (that belongs with the settings API, C15a; `_reconcile` is the function it will call).

## Verification
- Tests first, watched failing (missing module, missing column), then green. Mutation checks on `apply_batch` and `sync_connection` (each broke the named test): cancellations applied on an incomplete batch, unreadable events not counted as present, sweep without the window, revive past the deadline, `override` overwritten, template ownership unchecked, `joined` made cancellable; token written for an incomplete batch, no 410 fallback, no 6-hour rule, `last_full_sync_at` set on incremental, suspended users not filtered. One mutation survived by design: dropping the `user_id` filter in the missing-event sweep, because the connection filter already implies it (it stays as a second guard).
- Covered: the plan's lists for C8 and C8b; per-user isolation with the same source ids on two users; hostile input; all-day, offset, midnight-crossing, a New York series across the 2026-11-01 DST change (13:00Z before, 14:00Z after), moving and cancelling one instance of a series; end to end through `Scheduler.tick_sync` with `FakeGoogleCalendar`.
- Local checks: `ruff check .`, `ruff format --check .` (pinned 0.17.3), the full pytest suite on a Homebrew Postgres 17 (result in the PR body), migration round trip 0011 to 0012 and back on a scratch database, one head.
- **Not verified:** a real Google calendar (every body is synthetic until the C5 live step), a real scheduler process running the job against Google, DST for events that arrive without an offset (parse falls back to the `timeZone` field; C6 covers it, C8 only stores the result).

## Operate / roll back
- **Server steps before merge: none.** `CALENDAR_ENABLED` stays false in production, so the job is not registered and the scheduler is unchanged. Migration `0012` adds one nullable column and runs with the deploy's `migrate` step. No required variable.
- To switch on (after C4 merges): set `CALENDAR_ENABLED=true`, recreate `scheduler` and `web`. Connections whose `last_sync_at` is null sync within a minute. Logs: `docker compose logs --tail 50 scheduler` (`calendar sync for connection N failed (Type)` per failure, never a title, link or token).
- Reconnect flows (C3, C4, C13) should clear `last_error_at` so a reconnect syncs at once rather than waiting out the 5-minute failure cool-down.
- Roll back: revert the PR; `alembic downgrade 0011` drops the column (it only records the last full listing). Rows already written stay and are harmless.

## Follow-ups
- **C13** must turn a recorded `AuthRevoked` into `needs_reconnect` (reason `revoked`) with the notification, and 30 minutes of failures into `degraded`; until then a revoked connection is retried every 5 minutes and shows only `last_error`.
- **C12** owns what happens to a scheduled row past its deadline, the `skipped`/`failed` vocabulary and the 3-minute re-check; it must also move a `joined` row to `completed` with the meeting (spec 7.7). A cancelled event whose bot would not stop leaves the join `joined` and is not retried (the stub does not come again); the bot ends on Vexa's timeouts.
- **C15a**: a rule or template change should call `_reconcile` over the stored rows (the template is captured when the join row is made; the rule is re-read only when an event arrives in a batch).
- A join for an event whose link is recognised but not joinable (Teams until T1) is not created; T1 must revisit `_reconcile`.
- C10b's sweep deletes ended events after 2 days; the join outlives its event row (`ON DELETE SET NULL`), as designed.
